## [3.0.0] — Unreleased

### Overview

Version 3.0.0 is a major release relative to the last public line (2.0.x). It has two strands. The first **generalises the expectation tensor framework to multiple attributes per event** (multi-attribute expectation tensors, MAETs), adds the pre-MAET preprocessing primitives that feed them, and makes the consumer-facing entry points polymorphic on input shape with consumer-level batching. The second is **performance**: a new analytical decomposition (the Möbius method) alongside Bulger's method, a per-call cost-model dispatcher, kernel truncation and precision controls, and batching refinements throughout. The API changes that make this a major bump are listed under *Changed* and *Removed* below and in [MIGRATION.md](MIGRATION.md).

**Strand 1: multi-attribute expectation tensors.**

This release generalises the expectation tensor framework to **multiple attributes per event** (multi-attribute expectation tensors, MAETs). This lets the toolbox handle questions that the single-attribute treatment of v2.0 could not: locating motif recurrences over time, probe-tone scanning on irregularly timed contexts, polyphonic voice-aware analyses, and multi-quantity similarity (e.g., pitch combined with register, timbre, or metrical position) with the same closed-form analytical cosine-similarity inner product that underlies the single-attribute case.

Two cross-event preprocessing primitives, `differenceEvents` and `bindEvents`, support analyses based on inter-event differences and on n-tuples of consecutive events. A utility for sequential analysis, `continuity`, also accompanies the main additions. A categorical-encoding utility, `simplexVertices`, supplies equidistant vertex coordinates for simplex-coded categorical attributes (voice, instrument, etc.) suitable for MAET inputs.

This release also adds **soft (`sigma > 0`) support to the structural measures `sameness` and `coherence`** — both gain an optional positive `sigma` argument that softens the discrete equality / ordering tests against Gaussian positional uncertainty — and **a `sigmaSpace` flag, shared across `sameness`, `coherence`, and `nTupleEntropy`** (whose `sigma` argument already existed in v2.0), controlling whether `sigma` is interpreted as positional uncertainty on each event (the new default, propagated through index sharing among derived intervals) or as independent uncertainty on each derived interval (matching the v2.0 numerical behaviour of `nTupleEntropy` at `sigma > 0`). A separate strand adds **Monte Carlo sigma support to the Argand-DFT family** via the new `dftCircularSimulate` function: `balanceCircular`, `evennessCircular`, and `projCentroid` accept an optional `sigma` argument, with closed-form analytical damping where the geometry permits it (`projCentroid`, since the projection is linear in $F(0)$) and Monte Carlo where it does not (`balanceCircular`, `evennessCircular`).

The first strand also brings the **unification of dispatch and the addition of consumer-level batching**. The Python entry points `eval_maet`, `sim_maet`, and `entropy_maet` are now polymorphic: each accepts a single density object, a list of densities, or raw arrays for either single-multiset or batched-multiset evaluation. The MATLAB equivalents are likewise extended where each language idiomatically permits. The harmony, entropy, and consonance wrappers (`tensorHarmonicity`, `templateHarmonicity`, `virtualPitches`, `spectralEntropy`) accept 2-D pitch matrices for batched evaluation. The DFT-equivariant family (`dftCircular`, `meanOffset`, `edges`, `projCentroid`, `circApm`), the structural-measure family (`coherence`, `sameness`, `nTupleEntropy`), and the Monte Carlo functions (`balanceCircular`, `evennessCircular`) all gain batched-input dispatch. Every batched path uses canonical-form deduplication to collapse symmetry-equivalent rows onto a single cached computation. The v2.0 standalone entry points `cos_sim_exp_tens_raw`, `eval_exp_tens_raw`, `batch_cos_sim_exp_tens`, and `batchCosSimExpTens` are removed, every call they served being a mode of the unified entry points.

This strand is additive: existing v2.0 single-attribute calling conventions for `buildMaet`, `evalMaet`, `simMaet`, and `entropyMaet` are preserved unchanged, the single-multiset case being the $A = N = 1$ corner of the one density type, `MaetDensity`. The new multi-attribute calling form is dispatched on input shape (a cell / list of per-attribute arrays for `p`) and is otherwise separate. The structural and Argand-DFT extensions are likewise additive at `sigma = 0`; a documented numerical change to `nTupleEntropy` at `sigma > 0` is described in [MIGRATION.md](MIGRATION.md) and below.

**Strand 2: performance.** The headline gains come from two largely independent sub-strands that compound where they overlap:

1. **Mathematical: a new analytical decomposition for the underlying sums.**

   Three core quantities underlie the closed-form expectation-tensor calculus: the **inner product** $\langle T_x, T_y \rangle = \int T_x T_y \, \mathrm{d}z$ between two tensors (which underlies cosine similarity, windowed similarity, and Rényi-2 entropy); **point evaluation** $T(q)$ of a single tensor at a query (a sum of Gaussian-kernel contributions, one per source $r$-tuple — no integration involved at the level of the quantity, since $T$ is already the density. Note that the *Möbius realisation* of point evaluation and total mass is nonetheless grid-free only in absolute mode; in relative mode it integrates the translation marginal on a u-grid — see the relative-mode note below); and **total mass** $Z = \int T \, \mathrm{d}z$ of a single tensor (which converts $T$ to a probability density via $T/Z$ and appears in the denominator of Rényi-2 entropy and other normalised quantities). All three reduce to sums over slot-tuples: a double sum (one $r$-tuple per side) for the inner product, a single sum for the other two. v2.0 already evaluated the inner product analytically via *Bulger's method*, and the others are evaluated via an explicit centres-array route. v3 adds a new decomposition of these sums, **the Möbius method**, that scales far better at high $r$ and high $K$ and uniformly covers all three.

   **Bulger's method** (v1, carried unchanged into v2.0) is specific to the inner product. It organises the slot-tuple sum by taking combinations on one side and permutations on the other, exploiting the within-tuple multinomial symmetry to avoid enumerating equivalent orderings. The asymmetric combinations-vs-permutations organisation requires two sides to be present, so the method does not extend to point evaluation or total mass.

   **The Möbius method**, new in v3, is a different decomposition that applies uniformly to all three quantities. The slot-tuple sum is rewritten via Möbius inversion on the partition lattice: the distinct-index constraint becomes an alternating sum over set partitions of the slot indices, with each partition's term factorising across its blocks. For the **inner product** specifically, the partition decomposition combines with **orbit collapse** under the joint slot-permutation symmetry — many partition-pairs are redundant in the sense of contributing identically to the sum, so each redundant family is summed once with a counted multiplicity rather than walked term-by-term. This collapses the $B_r^2$ partition-pair count down to $|\Omega_r|$ orbit equivalence classes (4, 10, 33, 92, 306, 948, 3210 for $r = 2, \ldots, 8$, versus $B_r^2$ as large as $\sim 1.7 \times 10^7$ at $r = 8$). For **point evaluation** and **total mass** there is only one side, so no joint symmetry to exploit and no collapse to perform; cost scales with the bare partition count $|\Pi_r| = B_r$.

   The underlying inclusion-exclusion technique itself has a longer history in MPT: it was first published in Milne et al. 2011 — framed there as inclusion-exclusion rather than as Möbius inversion on the partition lattice (the two are equivalent formulations) — and has been used in the toolbox since v1 for *numerical* computation of discrete tensors. What is new in v3 is its application as an analytical decomposition of the slot-tuple sum, its combination with orbit collapse for the inner product, and its uniform extension across all three core quantities. The decomposition is grid-free in **absolute** mode (each partition block collapses to an $O(K)$ event sum evaluated directly at the query). In **relative** mode it is *not* grid-free: the relative tensor is the marginal of the absolute tensor over the shared translation $u$, and the alternating partition sum only factorises across slots at fixed $u$, so the Möbius method integrates over a u-grid of $N_u$ points (as the centres/Bulger path avoids by carrying the closed-form relative Gaussian per tuple instead). Removing that $u$-integral analytically would re-expand the per-partition product of block sums back into an $O(K^r)$ tuple enumeration, which is exactly what the decomposition exists to avoid; the u-grid trades that enumeration for an $N_u$ factor. The u-grid is therefore intrinsic to the relative-mode realisation — but the $K$ factor at each grid node is not: in the non-periodic case each partition block's integrand factor separates exactly into a variance prefactor times a shifted read-back of one of $r$ precomputed smoothed event distributions $S_m$ (one per block size, width $\sigma/\sqrt{m}$), so `evalOrbitRel` carries three strategies. The *direct* strategy costs $B_r \cdot r \cdot K \cdot N_u$ per query. The *factored* strategy costs $B_r \cdot r \cdot N_u$ per query after an amortised $O(\sum_m N_{\text{fine},m} \cdot K)$ tabulation. The *spectral* strategy removes the u-grid entirely: the translation integral constrains each partition's total mode index to zero, so every partition is a coefficient of a product of per-block Fourier spectra, and the spectra of a Gaussian mixture are closed form. Its cost is $O(K \cdot M)$ for the coefficients plus a per-query cost in $M$ alone, where $M \propto L / \sigma$ is the mode count over the period $L$ (the true period in periodic mode; a padded embedding period on the line) and $K$ has left the per-query term altogether. A per-call cost gate selects among the three. The factored read-back (local quintic interpolation, identical stencil in both languages) targets a relative accuracy at the kernel-truncation floor $\exp(-k^2/2)$ set by `truncation_sigmas` (clamped to $[10^{-12}, 10^{-3}]$; the factory default $k = 6$ targets $\exp(-18) \approx 1.5 \times 10^{-8}$, and $k = \infty$ targets $10^{-12}$, the noise level of the u-grid quadrature itself). In periodic relative mode the factored and spectral strategies apply where the per-block variance/mean reduction survives wrapping — the truncation window and each query's position span must both fit within half the circle — and the direct strategy covers the rest. All three figures compare with the grid-free $B_r \cdot r \cdot K$ of absolute mode.

   **How the Möbius and Bulger methods relate.** For the **inner product** they are alternative decompositions of the same analytical integral. On any given inner-product call the dispatcher picks one and computes the value via that decomposition; the two are not combined within a single call. This exclusivity is pragmatic, not mathematical — both methods already exhaust the same underlying slot-permutation symmetry, just along different routes, so there is no natural way to combine them that would gain over picking the better of the two. Each has a different cost-scaling profile: Bulger's method has essentially no per-call fixed overhead beyond the slot-tuple loop; the Möbius method carries fixed per-call overhead (orbit-table lookup, $|\Omega_r|$ tensor contractions) that must be amortised over the savings from orbit collapse. Bulger's method therefore tends to win at small $r$ and small $K$ (short slot-tuple loops, Möbius's overhead doesn't pay off); the Möbius method wins decisively at large $r$ or large $K$. The cost-model dispatcher in strand 2 picks the cheaper of the two per call. For **point evaluation** and **total mass** Bulger's method does not apply, so there is no two-decomposition choice; the Möbius method here is an *efficiency alternative* to the centres-array route — same analytical value, computed without materialising the explicit $r$-tuple centres array, which matters most in the large-$K$ / high-$r$ regime where that array would dominate memory.

2. **Computational: dispatching, kernel precision, kernel truncation, and batching refinements.** A per-call cost-model dispatcher selects whichever decomposition is faster for each call; routing follows from structure, the declared measure, and the cost model alone, with no timing probe. Two new kernel-evaluation controls — `truncation_sigmas` (skip Gaussian contributions beyond $k$ standard deviations from a centre) and `kernel_precision` (`'single'` instead of `'double'` for the kernel matrix multiplication; ~2× speedup, ~7 sig fig precision) — apply to the centres-path consumers (eval, cos-sim, entropy) at user request and roughly compound with the mathematical-strand gains. Set per call or globally via the new toolbox-wide defaults API (`mpt.set_default` / `mptDefaults`). **Lazy density-struct construction** in `buildMaet` is also part of this strand: expensive density fields (`U_perm`, `wJ`, `V_comb`, `wV_comb`) are deferred until a consumer needs them — most strand-1 consumers do not need them. Finally, **batched workloads use grouped contractions** rather than sequential per-item loops: `tensorHarmonicity`'s batched mode deduplicates and batches its rows, and the Möbius relative-mode evaluator vectorises its u-grid and offers a factored integrand strategy that removes the per-node $K$ factor for batched workloads (accuracy tied to `truncation_sigmas`; see the relative-mode note above and the evaluator bullet below). Each is detailed in the corresponding section below.

v3 also exposes **Rényi-2 differential entropy** $H_2 = -\log_b \langle T, T\rangle / Z^2$ as `method='renyi2'` on `entropyMaet`. The analytical route was conceptually available in v2.0 (it requires only the inner product and total mass, both already analytical); v3 wires it up as a user-facing option and gains efficiency at high $r$ / $K$ via the Möbius method. **Shannon differential entropy** has no closed form in any version and is unchanged — `method='shannon'` continues to use a numerical grid.

Additional improvements outside the two strands: a new pre-tensor preprocessing primitive **`translateAttributes` / `translate_attributes`** shifts selected attributes' values by a chosen offset (unwrapped on periodic attributes, with the periodic kernel handling wrap downstream; a structural no-op on relative attributes); this is the translation route to sliding comparison along an attribute, complementary to the windowed `sweptSimilarity`, and handles multi-slot attributes ($K_{a, n} > 1$) without ambiguity since every slot translates by the same offset. Where that sliding comparison is a *sweep* — one context density against many uniform translates of one query — **`sweepSimMaet` / `sweep_sim_maet`** evaluates the whole sweep in one pass rather than one inner product per offset, by separating each tuple pair's contribution into a fixed shape weight and a Gaussian in the offset.

This strand is additive in its API: existing calling conventions are preserved, and the method dispatcher (`'auto'`) reproduces v2.0's decomposition choice (Bulger's method) at the floating-point level in standard regimes. The new method choice is exposed via a `method` keyword on `simMaet`, `evalMaet`, and `entropyMaet` (`simMaet` accepts `'auto'`, `'bulger'`, `'centres'`, `'mobius'`, and `'contract'`; `evalMaet` accepts `'auto'`, `'centres'`, and `'mobius'`); `'auto'` is the default. `kernel_precision` defaults to `'double'`. **`truncation_sigmas` now defaults to `6`** (see *Changed* below): default-configured output is therefore a ~6-significant-figure approximation of the untruncated v2.0 result rather than bit-identical to it, and exact untruncated numerics are recoverable at any time with `truncation_sigmas=inf`.

**Terminology used throughout.** There is one density type, the *multi-attribute expectation tensor* (MAET), built from *MA* = multi-attribute inputs (one or more coordinate axes per event, e.g. pitch alone, or pitch + onset time). The *single-multiset corner* of that type — one attribute and one event ($A = N = 1$) — is served by a speed branch of the general path rather than by a path of its own. *Tuple size* $r$ (or $r_a$ for attribute $a$) is the number of slots in each event's ordered-tuple expansion (e.g. $r = 3$ for triadic interval analysis). For each event $n$ and attribute $a$ the *effective slot count* $K_{\text{eff}, n, a}$ is the number of non-NaN entries; the *attribute width* $K_a$ is the constant maximum over events. *Ragged-K* inputs are those where $K_{\text{eff}, n, a}$ varies across events $n$ (e.g. a sequence mixing dyads, triads, and tetrads), so trailing NaN entries pad each event to the common width $K_a$. The Möbius method's *alternating partition sum* is the inclusion–exclusion sum over set partitions of an $r$-tuple, with signs derived from the Möbius function on the partition lattice; its agreement with enumeration is governed by `truncation_sigmas`, not by the slot margin $K_{\text{eff}, n, a} - r_a$. The *Bell number* $B_r$ is the count of set partitions of an $r$-element set ($B_2 = 2$, $B_3 = 5$, ..., $B_7 = 877$, $B_8 = 4140$); orbit-table size scales with $B_r$ and dominates the build cost beyond $r = 8$. *Inner product* (abbreviated *IP* throughout) refers to $\langle T_x, T_y \rangle$. *Canonical-form deduplication* refers to the batched-input optimisation introduced with unified dispatch (see *Added* below): rows that are symmetry-equivalent (e.g. permutations of the same slot multiset, transpositions in relative mode) are reduced to a canonical key, computed once, and the result mapped back to all matching rows. *ULP* = "unit in the last place", the smallest representable spacing in floating-point — a few-ULP difference between two computations is the order of bit-level noise from accumulation reordering and is invisible above three or four significant figures.

### Added

**Staff, articulation, and program columns.** A MusicXML score carries `staff` (which staff of a multi-staff part a note is written on — a keyboard part's right and left hands — as distinct from `voice`, since one staff commonly carries two voices) and the articulations `staccato`, `accent`, and `tenuto`. Those are not mutually exclusive, a note being able to carry more than one, so each is its own two-level column rather than one column with a level per marking; a merged tied note keeps a mark any of its segments carries, as it does `fermata`. A MIDI file carries `program`, the program change in force on that note's channel at its onset (0 where none was sent), which selects the instrument sound — informative in a multi-timbral file and constant in a single-instrument one.


**Encoding a categorical column into a pre-MAET (`'roles'` on `preMaetFromAttrTable` / `pre_maet_from_attr_table`).** A categorical column reaches the pre-MAET in one of three ways, and which one is a research question rather than a property of the data, so it is given at the conversion: `'separateAttributes'`, `'orderedMultiset'`, `'simplex'`, or `'drop'`. These are the three encodings the JMM article contrasts on BWV 347's voicing (Analysis 1.2), and they are named for the structure each produces. Voice-aware is `'orderedMultiset'` on the part with bound chords; simplex-voice is `'simplex'` with one event per note; voice-agnostic is that same grain with no role, which is simplex-voice without its voice attribute. The no-role reading at bound chords is a fourth thing and wants care: an event then holds the chord as an unordered multiset on every attribute, so two attributes describing the same notes pair every value of one with every value of the other — the soprano's pitch class with the bass's height — and matching rewards combinations the chord does not contain. Binding a note's attributes to each other needs one event per note. Both docstrings and the user guide say so.

The first two are **structural**: the level is realized as which attribute you are in, or as which position, so the binding of value to level is carried by the layout. They gather an event's rows into one event holding one slot per level, which needs `'chords', 'bind'` and an event that holds exactly one row per level; events that do not are dropped with a warning naming the count, since an analyst may well accept losing a few events to use an encoding. Only one category may be structural, because a structural category individuates the values sounding together and two of them give an attribute set that can never be fully populated — `voice × articulation` yields eight attributes of which at most four are ever filled; the refusal names the category already structural and the two ways out. A structural category splits every listed attribute except the event-level ones (`onset`), whose value belongs to the event rather than to the note: splitting the onset by voice would give four attributes carrying one number, and since the attributes multiply, the time factor would be raised to the fourth.

`'simplex'` is a **value**: the level becomes the coordinates of a vertex of a unit-edge regular simplex, carried as its own attribute read whole, and the binding is the tensor product of the two attributes at the event — which is why simplex coding gives additive partial credit across levels where the structural forms give a multiplicative AND. Each concurrently-sounding note is then its own event, so it needs `'chords', 'separate'`, unless a structural category is also given, in which case the simplex is tagged within each of its slots.

**`'groupBy'`** names the column whose equal values in consecutive rows make one event, generalizing the onset binding; the default is the grid position where the table has been gridded, and otherwise the onset within `'chordTolerance'`. An event is a contiguous run rather than every row sharing a value, so a bar number that comes round again after a repeat gives two events. On a gridded table the `onset` attribute reads the grid's onset, the event there being the grid point rather than whichever note happens to sit in the first slot.

**`selectPreMaet` / `select_pre_maet`.** A filter on a pre-MAET: keep a selection of its attributes (by index, by the name its spec carries, or by a mask) and of its events (by index or mask), in the order given. It knows nothing of where the pre-MAET came from, reading only the two levels every pre-MAET has. Attributes keep their tuple sizes and flags, so a selection cannot change what an attribute means, and an attribute holding several coordinates of one value moves whole because it is one attribute and not several. Selecting events may leave an attribute with no value at a kept event, which is allowed and means what it says. Selecting rows of a table remains the host language's job.


**`gridAttrTable` / `grid_attr_table`: sampling an attribute table on a grid.** One event per grid point, a note occupying the points from its onset up to but not including its end, so a held note replicates across the points it covers. The construction is the one Analysis 1.1 of the JMM article uses on BWV 347 — a sixteenth-note grid giving N = 272 — and reproducing that count is the function's acceptance test in both languages.

Each point opens a slice of the chosen length and a note belongs to every slice it overlaps, so a held note replicates across the slices it spans and a note shorter than the step still lands in one rather than falling between samples. A slice with nothing sounding becomes a row whose note columns are all missing. Those rows are kept rather than dropped: they contribute nothing to any density, but they hold the place that makes the event index a uniform index of time, which is what `bindEvents` and `differenceEvents` read, and dropping them is one selection away. `buildMaet` admits such events (see its entry below).

Three weight policies, saying what a slice takes from a note overlapping it. `'coverage'` (the default) takes the fraction of the slice the note fills — how the span is filled — which is Analysis 1.3's weighting, "the fraction of the eighth each note sounds". `'presence'` takes the note's full weight in every slice it appears in at all, however briefly: which notes are here, rather than how much of the span each occupies. That membership reading gives each slice the set of what occurs in it, whatever the step, and separates from coverage as the step grows relative to the notes: at a bar-length step a slice holds the set of what occurs in that bar, where coverage would hold a duration-weighted profile of it. `'item'` takes the fraction of the *note* in the slice, so its weight is distributed over the slices it spans and it counts once in total; because the kernel is linear in weight, this gives a density numerically identical to the ungridded one at `r = 1`, which both suites check against BWV 347 rather than assert.

**`sweptSimilarity` / `swept_similarity` compares nested objects of different widths.** For a nested attribute each side keeps its own `tags`, which say which slot belongs to which nesting group and so have the length of that side's own padded inner cardinality, while `r`, `[rel]`, and `[exch]` are shared (and `sigma`, `per`, and `period` are taken from the context), which is what one comparison constrains. A nested query can therefore be swept against a nested context of another width — a chorale's beat may hold seven notes where the cadential prototype swept against it holds two — as `simMaet` also admits. A flat side against a nested one is refused.

**`locate` places each window attribute by its own rule.** With several window attributes each may be placed by its own rule — pitch by the query's centroid, time by its first onset — given as a per-attribute `dict` in Python and in MATLAB as the `{a, rule; ...}` map (`a` an attribute index) that `sweep` and `window` also take; an attribute the map does not name takes `'centroid'`, and a bare rule applies to every window attribute.

**The conversion reads only the columns it is asked for.** `'duration'`, `'velocity'`, `'part'`, `'measure'`, `'soundingDuration'`, `'weight'`, `'noteNumber'`, and `'fermata'` are read only where something names them — a `'specs'` entry, a `'weights'` policy, or `'parts'` — each raising where it is asked for and absent. A table of two columns, `onsetSeconds` and `pitch`, therefore converts: a table from an experiment, a corpus extract, or the Online Supplement's grammar analysis carries none of the others.

**`addSpectra` / `add_spectra` gains a pre-MAET form.** `addSpectra(pm, mode, ..., 'attribute', a)` expands attribute `a` of every event at once and returns a pre-MAET, as the other pre-MAET preprocessors do; the existing single-multiset form is unchanged and remains the primitive the harmony, entropy, and consonance functions call. The expansion multiplies the attribute's `K` by the number of partials and leaves `N` and the spec alone; a padded slot expands to padded partials at weight zero, a missing value having no spectrum, and since partials of one value differ in weight the result always carries weights. An attribute read in order at `r > 1` is refused, expansion scrambling positions that carry meaning. The bare `pAttr` / `wAttr` form the other preprocessors offer is not available here, its positional layout being indistinguishable from the single-multiset form.

Gridding composes: an already-gridded table regrids at a coarser step, and `gridAttrTable(gridAttrTable(T, fine), coarse)` equals `gridAttrTable(T, coarse)`. Each policy combines in the way that makes this hold — coverage sums and rescales by fine / coarse, item sums, presence takes the maximum — and both suites assert it across three policies and four step ratios. This is the route to a weighting the toolbox does not itself offer: weight the fine slices as the analysis requires and the weights carry through the coarsening, which is how the metrical weighting of Analysis 1.3 of the JMM article is reached. The coarse step must be a whole multiple of the fine one, the time base must be the one the table was gridded over, and `'weights'` must name the policy the table's weights already carry, since that is what fixes how they combine.

Coverage and presence differ only where a note does not fill a slice, so on a grid at or finer than the shortest note they agree, and BWV 347 at the sixteenth comes out identically under either. For what is sounding at a given moment the instrument is coverage on a fine grid, an instant having no duration and coverage approaching the momentary reading as the step shrinks.

The grid runs over beats or seconds — a metrical grid presupposing a beat map, which a score has and a bare performance may not, and saying so where the column is absent — and occupancy may be defined by the recorded duration or by the pedal-resolved one. The result adds `gridIndex`, a grid-onset column named for the unit gridded over, `noteId` (missing on an empty point, so the grid collapses back to the note table by grouping and nothing is lost), and `weight`. `duration` still means the note's own duration; the slice length is a property of the grid. `preMaetFromAttrTable` binds a gridded table on its grid position rather than on onsets, since the grid already says which rows share an event.

Because an empty grid point has no value for them, a gridded table's integer and boolean columns become pandas' nullable `Int64` and `boolean`; MATLAB, having no missing logical, gives a logical column as double.

**The JMM demos.** Each reads its score with `read_score`, samples it with `grid_attr_table` under the coverage weighting that is the article's own "fraction of the eighth each note sounds", and converts with `pre_maet_from_attr_table`. The calls that carry an analysis — `swept_similarity`, `sim_maet`, `build_maet`, and `pre_maet_from_attr_table` — are made in the demo body, so the argument list that decides an analysis (the window, what is dropped, the normalization, the three encodings' `roles` and `chords`) is visible where it is made, and the two languages read alike.


The JMM demos are named after the analyses they reproduce, numbered in one series per piece — 1.x Bach, 2.x Coltrane, 3.x Reich, 4.x the supplied parses — running across the article and the Online Supplement, so an analysis keeps its number wherever it is printed. Two of them, `demo_jmm_1_4_tonic_tuple_size` and `demo_jmm_3_3_xcorr`, reproduce analyses that appear in the Online Supplement (§7 and §10) rather than the article.

**`sweptSimilarity` / `swept_similarity` and `sweptEntropy` / `swept_entropy`: one placement rule, translation by default.** Each swept attribute has one list of *sweep values* (`'sweep'`, or `'start'` / `'stop'` / `'step'`), and one rule places everything: at each sweep value a translated query has its reference value `'queryRef'` there (it is translated by $\mu = s - \mathrm{queryRef}$), and a window has its reference value, its displacement zero, there. `'align'` says which of the two are placed: `'query'` (the default: attribute translation over the whole context, the canonical sweep, computed in one pass by `sweepSimMaet`; `'queryRef'` defaults to 0, so the sweep values are the offsets added to the query as written), `'both'` (query and window at each sweep value; `'queryRef'` defaults to the query's middle, so the window is aligned at the query's middle), `'window'` (a window only), or `'independent'` (a window at each value of one list and the query at each value of another, the correlogram; `'queryRef'` defaults to the query's middle). The translation applied at each sweep value is returned as a second output (`[S, mu] = sweptSimilarity(...)`; Python `return_offsets=True`), so a windowed sweep can be stepped across the context and read as offsets, which keep their meaning through differencing. A window is its shape followed by named options, MATLAB `{'gaussian', 'sd', 4}` (or the same as a struct), Python `{'shape': 'gaussian', 'sd': 4}`; its scale, `'width'` or `'sd'` (`'sd'` or `'decayRate'` for the exponentials), is always named, since a bare number could be read as either, and a positional `{shape, width}` is refused. A window that meets the query under `'both'` may be left out, and is then the smallest closed rectangle that, so placed, holds the query; a given window that leaves out some of the query's own events warns; a scale is required for `'window'`, `'independent'`, `sweptEntropy`, and `sweptMass`. Rectangles take `edges`, `'halfOpen'` (the default for a given width, right for tiling) or `'closed'`. A rectangle of given width also takes `'ref'`, the point of it placed at each sweep value: `'centre'` (the default), `'start'` (the window covers $[s, s + W)$), or `'end'` ($[s - W, s)$), so that the sweep values can be read as the windows' starts or ends; its default sweep values shift with it (tests: `test_swept_window_ref.py` / `.m`). Naming the attribute alone (`'sweep', a`; Python `sweep=a`) takes default sweep values: where the query is translated, every placement at which it overlaps the context (one period on a periodic attribute), stepped at no more than half the standard deviation of the profile's peaks, σ√(2/r), and at a whole fraction of the values' spacing where they lie on a lattice, so that every exact match is on the grid (onsets on whole beats with a half-width of 0.15 step at 1/7, not 0.15); where only a window is placed, the context's extent, stepped at half the window's sd, since the profile then changes on the scale of the window; for largely separate windows, as when the profile's values are to be used as data, give `'step'` as half the window's width ($\sqrt{3}$ sd), neighbouring windows overlapping by half. A pure rectangle, whose profile is piecewise constant, takes instead its pieces: the breakpoints where an event enters or leaves the window, each piece sampled just inside both its ends. `'start'`, `'stop'`, and `'step'` each override one default, and take a bare number where one attribute is swept (`'sweep', 2, 'step', 0.5`). The query is windowed, where wanted, by `weightEvents` before the call. The User Guide (§8.7) describes the arguments. Where the windowed context is fixed across the query's translations, they are computed in one pass through `sweepSimMaet` (a nested attribute on its contraction route, below), falling back to one comparison per translation only where no sweep route applies.

**The swept functions weight events through `weightEvents`.** Event weighting has one implementation (`internal.weightFactor`, `internal.resolveProfile`, `internal.resolveEdges`; Python `_weight_factor`, `_resolve_profile`, `_resolve_edges` in `preprocessing`), which `weightEvents` / `weight_events` and the swept functions both call. `weightEvents` takes `locate` (an event holding several values on the input attribute, such as a bound super-event, is reduced to one, by default the mean) and `edges` (`'closed'` for a rectangle including both edges). The windows take every `weightEvents` profile aligned at a reference value: the rectangle-Gaussian, the exponentials, including `'exponentialBefore'` and `'exponentialAfter'`, which extend to one side only (a struct / dict with `'sd'` or `'decayRate'`), and a function of the displacement; the serial-position profiles, anchored at the first and last events, are refused. A window on a periodic attribute wraps its displacement. Both languages; the factors agree between them to 4e-16.

**`sweepSimMaet` / `sweep_sim_maet`: a contraction route for nested attributes (`method = 'contract'`).** For a sweep over densities with a nested attribute — a bound, spectrally enriched pitch attribute, say — the mixture route would enumerate every nested tuple (every combination of the elements at every bound position, 12⁴ for twelve partials at each of four positions), and the orbit route declines nested attributes. Translating every value of an absolute attribute keeps the leaf kernel of the nested contraction a one-body product per coordinate, so the offsets can ride the contraction's batch axis, the axis the relative line integral already uses for its translation nodes, with each node kept rather than summed. The contraction route does that for each swept nested attribute, forms a swept flat attribute's per-attribute matrix at each translated value, forms the attributes that are not swept once, and takes the translation-invariant self inner products once from the ordinary contraction; the matrices then multiply and sum as in the nested inner product (JMM Eq. 3.4). A swept attribute must be absolute and isotropic, with no inner or intermediate relative unit; flat or nested, periodic or not. `'auto'` takes the route wherever a nested attribute is present and the contraction covers the densities. It computes each entry with the same kernel, truncation and per-level reduction as the per-offset comparison, so it agrees with it to floating point (bit-identically on the JMM 2.3 B2 panel), without the per-offset rebuild and dispatch: the B2 panel takes 3.0 s against 48.6 s for a comparison per offset. `sweptSimilarity` takes it through `sweepSimMaet` wherever it sweeps offsets in one pass. Both languages, with tests pinning the route to translate-and-compare for ordered and exchangeable levels, periodic and non-periodic pitch, a swept flat attribute beside a fixed nested one, and both normalizations.

**`buildMaet` / `build_maet` admit an event that is empty on an attribute.** An event carrying a time and no pitch — a grid slice with nothing sounding, a voice resting — admits no tuple on that attribute and therefore contributes nothing: the density, the inner product, and any entropy taken from them are numerically identical whether it is present or absent. What it keeps is its place in the event sequence, which is what `bindEvents` and `differenceEvents` read, and what makes the event index of a grid a uniform index of time.

The same holds for an event with *some* but too few values, ordered or unordered, flat or nested. A `NaN` is a position with no value, read as a value of weight 0, so every tuple through it vanishes and an event holding fewer than r values contributes nothing, as an event of weight 0 does; at r = K on an ordered attribute, one missing value removes the event. Since such an event may be a mistake, the build warns, once per call, with the number of events affected on each attribute (`buildMaet:tooFewValues`). An attribute whose positions, values and `NaN`s together, are fewer than r, so that no event could supply an r-tuple, is an error (`buildMaet:tooFewPositions`; on a nested attribute, `buildMaet:nestedInfeasible`).


**MIDI controller streams resolved at read.** Three of them change a note's own columns, and `readScore` / `read_score` resolves each. Sustain (CC64) and sostenuto (CC66) give `soundingDurationBeats` / `soundingDurationSeconds` beside the recorded durations: a note whose note-off falls while the pedal is down sounds until it comes up, or to the end of the file where it never does; sostenuto holds only what was already down when it was pressed; and the same note number struck again on the same channel damps what is left of the first, while the same pitch on another channel does not, since two channels may be two instruments. Pedal state and the damping rule are both per channel, and a channel belongs to the file rather than to a track. Either duration can feed an analysis, which is the choice the JMM manuscript already makes between notated and sustained fermata chords.

**Pitch bend is resolved into `pitch`, which is therefore floating point.** Bend is how microtonal music is carried in MIDI, in the one-channel-per-note idiom and under MPE alike, so a reader returning note numbers would return the wrong notes. The range is 2 semitones unless RPN 0 sets it, or an MPE Configuration Message (RPN 6 on channel 1 or 16) opens a zone, whose member channels take the 48-semitone MPE default; a file that bends without declaring either raises `readScore:bendRange`, since reading one at the other is wrong by a factor of 24. A note takes the last bend at or before its onset tick, so a bend sent immediately before a note-on, or at the same tick in either file order, tunes it. The number as recorded is kept in `noteNumber`, which is what note identity rests on.

**Channel volume (CC7) and expression (CC11) fold into a `weight` column**, as `(velocity/127) · (cc7/127)² · (cc11/127)²`, so that a passage played down by expression is not weighted as though it were at full strength. The squares are MIDI's specified default response for both controllers, an attenuation of 40·log10(cc/127) dB, cascaded and so multiplied; the velocity factor is linear because MIDI specifies no velocity-to-amplitude curve and because taking it linearly makes `weight` equal to the `'velocity'` weighting on any file that sends no controller. The formula is therefore a hybrid — the toolbox's velocity weighting corrected by the channel's specified gain — rather than an estimate of sounding amplitude, and the docstrings say so. `velocity` keeps the value as recorded, and `preMaetFromAttrTable` accepts `'weights', 'weight'`, and `'soundingDuration'`, `'weight'`, and `'noteNumber'` as attributes.

No other controller is read: a column holding a controller's value at a note's onset would look as though it carried the information and would not, since a ramp inside a held note is invisible in it.


**The score readers return a table (`readScore` / `read_score`).** A MATLAB `table` and a pandas `DataFrame`, one row per sounding note. The table is an ordinary object of its language, so it is inspected, sorted, joined, and filtered with the host language's own indexing and needs no toolbox function to read; `preMaetFromAttrTable` still takes a path, so the reader is called directly only when the table itself is wanted.

A MIDI file gives a `channel` column and a MusicXML score a `voice` column, and a column appears only where its source carries the information, so neither stands in for the other. `fermata` is a logical present only on a MusicXML score; a `'fermata'` attribute requested of a MIDI file raises. `part` is a categorical whose categories are the part names, in part order, so a part is selected by name. The source is held in the table's description (`Properties.Description`, `df.attrs['source']`). `'parts'` on `preMaetFromAttrTable` accepts part names as well as 1-based positions.

Python gains a dependency on pandas (>= 2.0).


#### Plotting a density

- **`plotMaet` / `plot_maet`.** Draws a density of one, two, or three drawn dimensions, dispatching on the dimensionality the density carries, `dim = r - rel`; four or more is refused. Three methods, each named for what it shows rather than for the geometry it uses, since the geometry is what changes with the dimensionality. **`kernels`** draws the model: one object per tuple centre — an ellipsoid, an ellipse, or a curve — shaped by the kernel's covariance and coloured by the density there. No grid is evaluated, so the cost is the number of centres rather than the volume, and it is where the shape of a relative kernel shows: the covariance is $I + J$, elongated by $\sqrt{r}$ along the all-ones diagonal and circular across it. At one dimension each curve is one tuple's own term, its width the kernel's and its height that tuple's weight, so the curves sum to the density and a peak can be seen to be one kernel or several. **`points`** draws the density sampled: one translucent mark per grid node above a threshold, three drawn dimensions only, since below that it samples what `density` already draws whole. **`density`** draws the density itself: a line, a textured translucent surface, or a stack of textured planes square to whichever axis is most nearly square to the view, a stack per axis shown one at a time so the picture changes as a rotation crosses the diagonal. At three dimensions it is a true volume rendering, the value read as an extinction per unit of path. The grid `points` and `density` evaluate is asked for as `'step'`, a spacing, or `'nodes'`, a count of steps across the range — the same request two ways — defaulting to 1200 steps at one and two dimensions and 120 at three, the grid being dim-dimensional. A periodic density's kernels are drawn again across each face they cross, so the wrap is cut by the face rather than missing from it. **`density` at three dimensions is MATLAB only**, resting on texture-mapped surfaces which matplotlib has no counterpart for; Python raises there naming `points`, and every other combination is in both languages. Python follows matplotlib's defaults rather than MATLAB's — no colour-map brightening, light panes, matplotlib's own camera and colour map — and takes `view` as matplotlib's `(elev, azim)` where MATLAB takes `[azimuth elevation]`, each following its own plotting library. Python's plotting needs `matplotlib`, which the toolbox does not require and which is imported when a plot is drawn rather than when `mpt` is imported, so `numpy` and `scipy` remain its only dependencies. §8.6 of the User Guide.

- **`points` has a resolution budget, and it is a MATLAB one.** A mark carries one depth across its whole face, so where two marks overlap the nearer hides the farther outright rather than blending, and every such contest reverses when the camera passes to the other side: the same cloud then draws differently from opposite directions, blobs gaining haloes from one of them. The automatic size and step keep the marks apart, holding as long as the grid is no finer than the axes can separate — about three points of screen per node, which depends on the figure's size and on any zoom as much as on the step. A step set by hand can ask for more; the drawing then warns once (`mpt:markOverlap`) and is camera-dependent until the figure is enlarged, zoomed, or the step coarsened. matplotlib depth-sorts and blends its marks, so the Python side has no budget, no automatic sizing, and no warning.

- **What the methods cost, measured.** The grid evaluation is around 85 per cent of the cost of either `points` or `density`, so the choice between them barely affects time to first picture. Per frame of a rotation they differ sharply, and not in the direction simplicity suggests: `points` marks go as the cube of the nodes per axis where a stack's planes go as the first power, giving 20 frames a second against 67 on a 121-node grid and 4 against 51 on a 241-node grid. `points` is chosen for what it shows — the samples stay discrete, so the grid is visible rather than interpolated away — and not for what it costs.

- **Transparency in MATLAB, and what it cost.** The obvious way to draw a volume — a scatter of semi-transparent marks, each taking its opacity from the density — is not dependable in MATLAB: given truecolour marks and unmapped opacity, they are drawn opaque as soon as the figure settles, while rendering correctly throughout a drag, so the picture at rest is not the one the opacities describe. The fault survived every mark size, sorting order, smoothing setting, point count, and opacity value tried. Mapped colour with the alphamap left scaled is rendered correctly, and is what `points` uses. Surfaces have their own version of it: per-vertex opacity (`FaceAlpha` `'interp'` or `'flat'`) renders a large surface blank, while `'texturemap'` for both the colour and the opacity renders correctly, and that is what the two- and three-dimensional `density` use. A stack of such planes then needs `SortMethod` `'childorder'`: under MATLAB's default depth sorting the nearest plane writes depth and every plane behind it is rejected rather than blended, so a stack of any depth reaches only the opacity of its frontmost plane — measured at 0.24 against the 1.00 its own `AlphaData` composites to. MathWorks has separately acknowledged an integer-rounding defect in alpha compositing by which many faint layers never accumulate to the colour they should; the same eight bits are why cutting a volume into more, thinner planes loses faint material rather than resolving it, and why there is one plane per plane of the volume. The note is here because the natural first implementation is the broken one, in every one of these cases.

#### A pre-MAET is one object

- **`packPreMaet` / `pack_pre_maet` and `unpackPreMaet` / `unpack_pre_maet`.** `pAttr`, `wAttr` and `specs` always travel together and always describe the same pre-MAET, so they are carried by one named-field object: a MATLAB struct with the fields `pAttr`, `wAttr` and `specs`, and a Python dict with the keys `p_attr`, `w_attr` and `specs`. It is a plain struct or dict rather than a class, so the parts stay ordinary cells, arrays and structs, and any of them may be read or replaced directly; `packPreMaet` validates the parts against one another, so a `wAttr` or `specs` of the wrong length, or a single attribute or spec passed unwrapped, is an error at the point it is written rather than further downstream. Every function that takes a pre-MAET takes it either whole or in its parts, and the two forms are the same call. The five preprocessing operators, `readPreMaet`, and `preMaetFromAttrTable` return the whole pre-MAET, and `unpackPreMaet` splits one back into the parts for the places that want them separately. Because the specs travel with it, a composition needs no threading: `differenceEvents(bindEvents(pm, [2 2]), [1 1])`. `buildMaet`, `evalMaet`, `simMaet` and `entropyMaet` take a whole pre-MAET wherever they take a density, since it holds everything a build needs; `showPreMaet` and `writePreMaet` take one. The weights argument is `wAttr` in every call form that names `pAttr`, matching what it is — one value matrix per attribute — and stays `w` on the single-multiset forms of the four polymorphic entry points, where a bare vector is legal. §6.1 of the User Guide.
- **Attributes and weights given per event.** An attribute's values may be written event by event: a cell (MATLAB) or list (Python) with one entry per event holding that event's values, a scalar, a vector, or empty for no value, so `{[60 64 67], 62, 64, 65}` / `[[60, 64, 67], 62, 64, 65]` is a triad followed by three single notes. It stands for the NaN-padded $K_a \times N$ matrix and is converted to it wherever a pre-MAET's parts are taken: `packPreMaet`, every pre-MAET preprocessor, `buildMaet` and the raw multi-attribute forms of `simMaet`, `evalMaet` and `entropyMaet`, `sweptSimilarity`, `sweptEntropy`, `sweptMass`, and `showPreMaet`. Weights may be given per event in the same way, each entry a scalar for all the event's values or a vector with one weight per value, and slots holding no value take weight 0. In Python a list is always read per event and a matrix is always a NumPy array; a flat list of scalars is one value per event, and a flat weight list of length $K_a \neq N$ is read per row. The documentation and examples use the per-event form where values are written by hand. Tests: `test_per_event.py` / `.m`.
- **Ordered attributes keep their slot positions.** On an ordered attribute a value's slot within its event is its level (a voice, a coordinate), so an empty slot (`NaN`) before or between values is kept wherever the pre-MAET goes. `showPreMaet` and `writePreMaet` write it as a blank, `(62, _, 67)` or `(_, 65)`, trailing empty slots being left off, and `readPreMaet` reads the blank back into the same slot, so the round trip through a CSV file is exact; unordered attributes are written compacted, as before. `showPreMaet` also now spreads a scalar, per-event, per-value, or empty weight entry across its attribute, as `buildMaet` does. Tests: `test_pre_maet_io.py` / `.m`.
- **`transformAttributes` passes absent values through.** A `NaN` slot (the padding of an event with fewer values than others) is carried through unchanged rather than refused as non-finite, so a chord-bearing attribute can be transformed; $\pm\infty$ is still refused.


- **A cell / list of pre-MAETs stands wherever a cell / list of densities does.** `simMaet`, `evalMaet` and `entropyMaet` take one, building each entry on the spot, so a set of multi-attribute items is scored in one call without a per-item build. This is a different sense of "batch" from the row-wise deduplication of a 2-D matrix of single multisets: rows there are commensurable and collapse to one computation per equivalence class, whereas each pre-MAET is a whole item with its own event count and geometry, so the entries are looped and nothing collapses — the saving is in the calling code, not in the arithmetic. The exception is a translation sweep, whose entries share one geometry and differ by a known offset: `sweepSimMaet` (the mixture route, or the orbit route for a periodic swept attribute) and `sweptSimilarity` compute it in one pass, whereas the translated copies from `translateAttributes`, passed to `simMaet` as a cell / list, are built and compared entry by entry, agreeing to floating-point at the per-entry cost. Workflow 3 of `demo_batchProcessing` / `demo_batch_processing` sets the two senses side by side. `verbose` governs these builds too, so a quiet call stays quiet. §6.1 of the User Guide.
- **`sweptSimilarity` and `sweptEntropy` take pre-MAETs.** Two for the similarity and one for the entropy, with the same six per-attribute overrides as `buildMaet`. The shared geometry is read from the context's specs; the two pre-MAETs of a comparison must agree on the structural geometry — `r`, `[rel]`, `[exch]`, and the nesting — while `sigma`, `per` and `period` may differ and are taken from the context, and a pre-MAET without specs is refused, since the specs are where the shared geometry is read from. `demo_helixBlend` / `demo_helix_blend`, which sweeps a pitch-height width, builds its two pre-MAETs once, leaves the swept width at NA in the spec so the printed table names it, and passes `'sigma', {[], s, []}` on each call.

- **A selective override form.** An override may name every attribute or be selective: a length-A cell (MATLAB) or list (Python) whose empty entries keep what the spec carries, so a sweep names only the parameter that varies and the vector cannot drift out of step with the attributes. It follows the convention `translateAttributes`'s `offsets` and `transformAttributes`'s `transforms` already use. `NaN` is not available for this, already meaning NA.

- **Input forms are documented in one order everywhere.** Every entry point that takes more than one shape of input lists them the same way: a single multiset first, where that applies; then the pre-MAET, the canonical entry for everything else; then a density built by `buildMaet`; then the raw positional multi-attribute form; then the list and batched forms.

- **All six per-attribute parameters override the specs at `buildMaet`.** `r`, `rel`, `exch`, `sigma`, `per` and `period` are all name-value arguments, resolved the same way: a supplied value wins over the specs for every attribute. A sweep over any of the six is therefore one call per value, with the pre-MAET left untouched, and needs no setter and no rewriting of the pre-MAET between iterations; `showPreMaet` reads the override too, so the table states what the build will use rather than what the pre-MAET holds. Section 4 of `demo_preMaetIo` / `demo_pre_maet_io` sweeps a width past a spec that carries a baseline. On a nested attribute `r`, `rel` and `exch` are per-level vectors, where a scalar override has no unambiguous reading, so there they are refused with a message saying the spec is the place to change them. In MATLAB an unrecognised name-value argument to `buildMaet` is an error naming it.

#### The pre-MAET carries its kernel parameters, and reads and writes as CSV

- **`specs` carries `sigma`, `per` and `period`.** A pre-MAET is the event sequence, its per-event–attribute element multisets, *and* the per-attribute parameters (Milne 2026, Def. 2.6), so the kernel geometry travels with the attributes it belongs to. The three scalars are optional in the pre-MAET and compulsory at the tensor: `buildMaet` takes an explicit argument first (so a width can be swept while the specs hold a baseline), then the spec, and otherwise raises naming the attribute. `NA` (`NaN`) is a third state, distinct from absent: a preprocessing step that cannot carry a parameter forward writes NA rather than a stale or invented value, `showPreMaet` prints `sigma = NA`, and the build refuses it with a message saying a step could not carry it forward. The five operators carry the geometry accordingly — `bindEvents`, `translateAttributes` and `weightEvents` unchanged; `differenceEvents` scaling a width by $\sqrt{\binom{2k}{k}}$ at order $k$ (the $\sqrt{2}$ of a first difference) and announcing that it did; `transformAttributes` scaling by the gain of an affine map or a conversion within `midi`/`cents`/`octave`, and writing NA under anything non-linear — NA meaning not that a width would be meaningless in the new coordinate (a $\sigma$ on a log axis expresses a ratio rather than a difference) but that no canonical value carries over, the local scaling varying across the range. A kernel covariance, being in squared units, takes the factor itself where a width takes its root. §6.3 of the User Guide.

- **`readPreMaet` / `read_pre_maet` and `writePreMaet` / `write_pre_maet`.** A pre-MAET is a table, so it is a spreadsheet: these move one between the toolbox and a CSV that Excel or Numbers can edit, and a pre-MAET laid out by hand builds with nothing further supplied. The cells use the notation of the article and of `showPreMaet` — which takes `'format', 'csv'` and owns the rendering — so the writer and the reader are inverse and a round trip is byte-exact, for flat attributes, for nested attributes with weights, and for ragged events. A nested attribute's `tags` are reconstructed from the bracket structure of its cells and never written down; weights are omitted where they are all exactly 1, a bare value already meaning unit weight; and a kernel covariance is carried as the flag and three scalars that generate it, `cov(differenced=..., sd_value=..., sd_interval=..., sd_shift=...)`, recovered from an existing matrix by decomposition and verified by rebuilding it, so a covariance outside that family is refused rather than silently replaced by the nearest member. CSV output is byte-identical between the two languages. `demo_preMaetIo` / `demo_pre_maet_io` works through markdown, LaTeX, CSV out and CSV back on one pre-MAET. §6.4 of the User Guide.

#### Viewing a pre-MAET

- **`showPreMaet` / `show_pre_maet`.** Prints a pre-MAET as a table, in the layout of the pre-MAET tables of Milne (2026): one row per attribute, headed by the parameters that determine its density ($\sigma$, $r$, `[rel]`, `[per]`, and the period where periodic), and one column per event, its cells holding the elements from which the admitted tuples are formed. Because the pre-MAET is the framework's interface, the table is a complete statement of what a subsequent `simMaet`, `entropyMaet`, or `evalMaet` call will compute. Cells take braces where the attribute is unordered and parentheses where it is ordered, bracketed level by level when nested, so an ordered run of unordered chords reads `({62, 65, 69, 72}, {55, 59, 62, 65}, {60, 64, 67})`; a single element is bare at the top level but keeps its brackets inside a nest, so the level stays visible. Non-uniform weights appear as parenthesized superscripts, `60^(0.6)`; an attribute carrying a kernel covariance is named by its shape rather than having a matrix printed in the row. Either input form is accepted, a built density or the pre-MAET itself with the kernel parameters supplied alongside. `maxEvents` and `maxElements` elide a long passage's middle columns and a large multiset's tail, after the manner of the article's own tables. The default rendering is markdown, deliberately plain ASCII so that its column widths are identical in the two languages and it survives any terminal encoding; `'format', 'latex'` emits a `booktabs` tabular in the article's own markup, with optional `caption` and `label`, so that a manuscript's pre-MAET table can be generated from the code that runs the analysis. Every multi-attribute demo prints its pre-MAET immediately before the call that consumes it, and `demo_preprocessing` prints one after each preprocessing operation, so that each operation's effect on values, weights, and level structure is read off the table rather than described. §6.2 of the User Guide.

#### Multi-attribute expectation tensors

- **MAET calling form for `buildMaet`, `evalMaet`, `simMaet`, `entropyMaet`.** Each now accepts a multi-attribute density specification alongside the v2.0 single-attribute form. A MAET carries $A$ attributes, each with its own tuple size $r_a$, per-event slot count $K_a$, $\sigma$, `rel`, `per`, and `period`. The density factorises as a product of per-attribute Gaussian-mixture kernels, and the cosine-similarity inner product factorises analytically in the same way. The single-attribute case is the special case $A = 1$. See Milne (2026) for the mathematical formulation, and User Guide §8 for its use.

- **`MaetDensity`.** Tagged dataclass (Python) / tagged struct (MATLAB) produced by `buildMaet`. It is the toolbox's single density type: the single-multiset form is its $A = N = 1$ corner, served by a speed branch of the general path rather than by a type of its own. `evalMaet`, `simMaet`, and `entropyMaet` dispatch on the tag.

#### Cross-event preprocessing: `differenceEvents` and `bindEvents`

- **`differenceEvents`.** Preprocessing helper that replaces each attribute's event sequence with inter-event differences before tensor construction. Signature `differenceEvents(pm, diffOrders, 'circular', false)` (or the pre-MAET in its parts, `pAttr, wAttr`), with the `circular` Name-Value (MATLAB) / keyword-only (Python) flag described below. Per-attribute differencing order $k$ produces the $k$-th finite differences across events (reducing the event count by $k$ unless `circular` is set). Differences are emitted as raw signed subtractions regardless of periodicity; the mod-period wrap on periodic attributes is applied by the kernel at MAET-construction time, downstream of `differenceEvents`, in line with the toolbox-wide convention that pre-MAET preprocessing primitives produce raw values and the kernel handles wrap (the same convention `translateAttributes` follows on periodic absolute attributes). Weights propagate as rolling products of width $k + 1$, interpretable as the probability that all constituents of a difference are jointly perceived. An attribute is differenceable only where its positions keep their identity across events — ordered (`[exch] = 0`) or singleton at every level — since a multiset of more than one value has no positional correspondence; see User Guide §7 (Preprocessing). Output feeds directly into `buildMaet`. This supports analyses over interval content, IOIs, and higher-order differences without needing a dedicated interval representation.

- **`bindEvents`.** Preprocessing helper that gathers consecutive events into super-events: for each attribute $a$ a sliding window of width $L_a$ (`bindOrders`) is laid across the events, and the $L_a$ events it covers are nested into a single output attribute, the bound events forming an ordered outer level (`[exch] = 0` by default, lossless) and each event's own element multiset the inner level, whose geometry is read from the incoming spec. The outer level defaults to $r = L_a$ (reading the whole bound window), `[exch] = 0`, `[rel] = 0`; `[rel] = 1` on the outer level of an absolute attribute gives the global-transposition quotient. An attribute with $L_a = 1$ is not nested and carries the element multiset of the last event of each span. Each super-event spans $\max_a L_a$ events and is end-aligned to the last of them, the alignment `differenceEvents` uses, so differencing then binding equals binding then differencing. The effective weight of a bound super-event is the product of its constituent events' weights, matching the differencing rule. Default output has $N - \max_a L_a + 1$ super-events; a `circular` option produces $N$ by wrapping around the input sequence, and a `step` greater than 1 hops the windows. Composes with `differenceEvents`: the pipeline `differenceEvents` $\to$ `bindEvents` $\to$ `buildMaet` $\to$ `entropyMaet` recovers the n-tuple entropy of Milne & Dean (2016) at $\sigma \to 0$ and uniform weights, and extends it to the smoothed continuous case, weighted events, and non-periodic domains; the bound MAET supports cosine-similarity comparison of n-tuple distributions across pieces and the rest of the MAET pipeline. Used without preceding differencing, it produces n-grams in absolute pitch or time register, useful when register or absolute timing carries musical information that the differenced view discards. Inputs may hold any number of values per event, which is what polyphonic binding needs.

- **Circular event-sequence differencing.** A `circular` Name-Value (MATLAB) / keyword-only (Python) argument, default `false`, makes the difference operator wrap at the sequence boundary: $\Delta p_a(n) = p_a(n) - p_a(\mathrm{prev}(n))$ with $\mathrm{prev}(1) = N$. Each attribute's output retains $N$ events at every order; no leading-event drop is needed for per-attribute order alignment. Periodic attributes are handled as in the non-circular case — values are emitted as raw signed differences, with the kernel applying the mod-period wrap at evaluation time. The circular variant is the natural companion to `bindEvents`' `circular` flag, and is mathematically sensible in the same settings: cyclic event sequences (looped rhythms, ostinati) in which the boundary difference is a genuine inter-event interval rather than an artefact of truncation. Per-event weights propagate as a rolling product with cyclic indexing under `circular = true`, paralleling the non-circular rolling product. Circular mode requires $\max_a k_a < N$ (the wrap consumes the entire cycle at $k = N$); higher orders raise an error.

- **`nTupleEntropy` composition.** `nTupleEntropy` / `n_tuple_entropy` is the canonical composition of circular differencing with circular binding: cyclic first differences over the $N$-cycle of input events, bound at order $L = n$ into $N$ super-events, with the resulting MAET density's entropy reducing to the integer-step $n$-tuple-histogram entropy in the $\sigma \to 0$ limit (Section §2.3 of the JMM manuscript). The toolbox's implementation composes the two primitives directly.


- **`bindEvents` binds by a run of equal values.** `'groupBy'` / `group_by` names an attribute (by index or by name) whose consecutive equal values gather into one super-event, in place of the fixed sliding window: a new group begins wherever that value changes, so the groups are read from the data and may differ in length. This is the form a supplied structure takes when it does not come in uniform blocks --- the positions of one chord's derivation path, the notes of one bar, the frames of one gesture. The outer level is ragged: each super-event is padded to the largest group's size with NaN values at zero weight, which the nested inner product already consumes, and `'rOuter'` / `r_outer` says how many positions a tuple takes, defaulting to the smallest group's size --- the largest tuple size at which every group is feasible. The grouping attribute must carry one value per event (constancy across several is ambiguous), `'groupAtol'` / `group_atol` sets the tolerance for equality, and `'groupBy'` and `bindOrders` are mutually exclusive. `demo_jmm_4_1_parse` is the worked case.

#### `translateAttributes` / `translate_attributes`

- **Pre-MAET preprocessing helper.** Shifts selected attributes' values by a chosen offset: `pm = translateAttributes(pm0, offsets, ...)`, or the pre-MAET in its parts, `pAttr, wAttr`. Weights and specs pass through unchanged and the output feeds directly into `buildMaet` or a further pre-MAET step. Sits in the preprocessing family alongside `differenceEvents` and `bindEvents`, but is per-attribute and event-local (no cross-event correspondence) whereas its siblings are cross-event.

- **Sliding-comparison primitive.** Provides the **pre-tensor** route to a sliding comparison along an attribute: for each candidate offset $\mu$ on a sweep grid, translate the events and compute a similarity against an un-shifted reference, then read off the peak. Complements the windowed `sweptSimilarity` route, which reweights the context's events by a window at each position. The two routes differ in two ways: locality (translation uses the query's intrinsic support; the windowed route uses an externally chosen window, decoupling the comparison region's scale from the query) and normalisation (translation preserves the symmetric cosine and bounds values in $[0, 1]$; the windowed route is magnitude-aware by default, with values that can exceed $1$ and asymmetric query/context roles). On periodic attributes both routes are well-defined and operationally interchangeable for whole-density alignment; on relative attributes a uniform translation is a no-op.

- **Geometry semantics.** Absolute attributes, periodic or not: `value + mu`, unwrapped — the wrapped periodic Gaussian kernel of `buildMaet` is invariant under any additive shift by a multiple of $P$, so no canonical wrap of the translated values is required; `per` and `period` are not consulted. **Relative attributes** (read per attribute from the outermost level of the specs): a uniform finite offset is a structural no-op (a uniform shift cancels in every within-tuple difference), so the attribute is left unchanged and `translateAttributes:noOp` (MATLAB) / `TranslateAttributesNoOpWarning` (Python) is emitted once per call; a non-uniform, per-value offset shifts the within-tuple differences and so applies.

- **Multi-slot attributes ($K_{a, n} > 1$) handled without ambiguity.** Every value in the per-event multiset is shifted by the same offset, so unlike event weighting — where a per-event scalar weight has to summarise multiple values' distances from a localising centre — translation has no analogous obstruction at $K_{a, n} > 1$.

- **Offset grammar.** `offsets` has one entry per attribute, applying to that attribute's $K_{\text{total}} \times N$ value matrix (one row per element of an event's multiset, counting every element of a nested one): empty (not translated); a scalar (broadcast to every value); or a $K_{\text{total}} \times 1$ column (per value; in Python a 1-D array). Offsets are held constant across events, which is what makes differencing and translation commute. NaN entries skip the corresponding value; ±Inf is refused. One call makes one translation; a translation sweep is `sweptSimilarity` or `sweepSimMaet`, which compute every offset in one pass.

- **Calling forms.** Python:

  ```python
  pm_t = translate_attributes(pm, [6.0, None])                  # one translation of attribute 1
  ```

  MATLAB:

  ```matlab
  pmT = translateAttributes(pm, {6, []});                        % one translation of attribute 1
  ```

  The MATLAB warning identifier is `translateAttributes:noOp`; the Python warning class is `TranslateAttributesNoOpWarning` (re-exported as `mpt.TranslateAttributesNoOpWarning`).

- **Manuscript context.** Translation is presented in the JMM manuscript's "Sliding comparisons" section as one of two parallel routes (the other being windowing by event weighting) for asking how a similarity profile varies along an attribute. The translation primitive is used in §6.1.3 (cadence-progression similarity under transposition) to demonstrate the translation route, with `sweptSimilarity` used in §6.1.4 for the windowed route. The two examples expose the operational differences (bounded vs magnitude-aware, symmetric vs asymmetric, locality coupled to query vs locality independent) in concrete musical settings.

#### `weightEvents` / `weight_events`

- **Pre-MAET preprocessing helper.** Computes a per-event window factor from values of an input attribute and writes the factor into the weight slot of a (possibly different) target attribute, multiplied into any weight already there. Joins `differenceEvents`, `bindEvents`, and `translateAttributes` as a pre-MAET preprocessing primitive — the per-event weight-modifying primitive, complementing the per-event value-modifying `translateAttributes` and the cross-event `differenceEvents` and `bindEvents`. Returns a pre-MAET that feeds directly into `buildMaet`.

- **Input attribute and target attribute are separate.** The signature takes `inputAttr` (the attribute supplying values to the window function) and `targetAttr` (the attribute whose weight slot receives the factor) as separate scalar indices. They may be equal (the input attribute weights itself — selecting pitch events by a range of pitches, for example) or distinct (the cross-attribute case, where e.g. time provides the values and pitch receives the factor). Multi-axis windowing — windowing on time *and* on register, both targeting pitch — is expressed as a sequence of `weightEvents` calls with the same `targetAttr`; the multiplicative composition into the target's weight slot makes this a clean idiom.

- **One value per event on the input.** Where an event holds several values on `inputAttr` (the onsets of a bound super-event, say), `locate` picks the one the profile is evaluated at: `'centroid'` (their mean, the default), `'start'`, `'end'`, or `'mid'`. The per-event factor is a $(1, N)$ row, broadcast across the target attribute's $K_{\text{target}}$ slots.

- **Window family.** The rectangle-Gaussian window is specified by three numeric parameters: a centre $c$, a width $w$ (the standard deviation, in absolute units of the input attribute), and a shape parameter $\gamma \in [0, 1]$. The factor is the peak-normalised convolution of a rectangle of half-width $w\sqrt{3\gamma}$ and a Gaussian of standard deviation $w\sqrt{1 - \gamma}$, so the window's total variance is $w^2$ for every value of $\gamma$. The extremes are pure Gaussian ($\gamma = 0$) and pure rectangle ($\gamma = 1$, with half-width $w\sqrt{3}$); intermediate $\gamma$ interpolates continuously between them. The pure rectangle is half-open, so rectangles a width apart share no event, unless `edges` is `'closed'`. The shape may instead be an exponential profile (`'exponential'`, `'exponentialBefore'`, `'exponentialAfter'`), a serial-position profile anchored at the first and last events (`'exponentialFromStart'`, `'exponentialFromEnd'`, `'uShape'`, `'uAsym'`), or a function of the displacement. Factor entries beyond `truncationSigmas` standard deviations from the centre are zeroed. Periodic input attributes wrap the difference $\delta = v - c$ used inside the factor to $[-P/2, P/2]$ before evaluation; stored values stay raw and the kernel handles value-axis periodicity downstream.

- **`dropInputAttr` (mandatory, no default).** A boolean. When `true` and `inputAttr != targetAttr`, removes the input attribute, its weights, and its spec from the returned pre-MAET. When `false`, the input attribute is preserved in the output. `dropInputAttr = true` paired with `inputAttr == targetAttr` raises an error (deleting the input would discard the factor just written to it). Callers must specify the flag; there is no default, the choice being destructive enough to be explicit at every call. Dropping is the standard convention for windowed-entropy and local-mass workflows, where the input attribute (typically time) provides the scaffolding for the window and is no longer needed once its values have been transferred to the target's weight slot.

- **Centre-shift identity.** With `inputAttr == targetAttr`, `weightEvents` followed by `translateAttributes` on the same attribute equals translation first then `weightEvents` at a shifted centre $c + \mu$ (the residual $v - c$ is preserved). The identity underlies the windowed-entropy and pre-tensor sliding-comparison constructions.

- **Canonical composition.** The pattern `weightEvents` (with `dropInputAttr=true`, `inputAttr` typically time, `targetAttr` typically pitch) → `buildMaet` → `entropyMaet` is the windowed-entropy construction (entropy of the local slice of a density visible through the window). Conceptually documented in USER_GUIDE §7 (Preprocessing).

- **Window scale is given by one of two Name-Value (Python: keyword-only) arguments, `sd` and `width`, of which exactly one must be supplied.** Both specify the same underlying scale on different terms: `sd` is the window's standard deviation (the parameter of the variance-normalised parameterisation above), while `width` is the *full support* of the rectangle at `shape = 1`. The conversion is `sd = width / (2 sqrt(3))`. The two conventions exist because each is the natural way to specify the kind of kernel a particular analysis is built around: Gaussian users typically think in standard deviations (`sd`), rectangle users typically think in full supports (`width`). Across the full `shape` family the SD is held constant regardless of which parameter the caller supplied (variance-normalised behaviour is preserved), so the only effect of the parameter choice is the numerical value the user types. This avoids a foot-gun: were `width` the standard deviation, writing `width = 0.25` to mean "rect of total support 0.25 QN" would silently give a rectangle with cutoff at $\pm 0.25 \sqrt 3 \approx \pm 0.433$ and capture roughly three times the intended events. `width = 0.25` means exactly that the rectangle covers $[-0.125, +0.125]$ as written, and no conversion helper is needed because the user names the parameter in the unit they are thinking in. Validation: supplying neither `sd` nor `width` (or supplying both) raises `TypeError` (Python) / `'weightEvents:sdWidthXor'` (MATLAB).

#### Events from symbolic scores: `readScore` / `read_score`, `preMaetFromAttrTable` / `pre_maet_from_attr_table`

- **MIDI and MusicXML input.** `readScore` parses a Standard MIDI File (format 0 or 1: tempo map, time signatures, running status, note-on at velocity 0, notes left open at track end) or a MusicXML score (`.musicxml`, `.xml` partwise or timewise, compressed `.mxl`: divisions, chords, ties, grace notes, backup/forward, `sound tempo` and metronome directions, `dynamics`) into a note table with onsets and durations in quarter-note beats and in seconds, MIDI pitch, velocity, part, channel (MIDI) or voice (MusicXML), bar, and, on a MusicXML score, a logical `fermata` flag (a merged tied note counting if any segment does), which `preMaetFromAttrTable` can carry as an attribute. Both parsers are self-contained in each language (no `mido`, no Audio Toolbox, no Java) and read the same file to the same table; `tests/data/` holds shared fixtures that both suites assert.
- **`preMaetFromAttrTable` builds a pre-MAET** from a path or a table: attributes chosen by name (pitch, onset, duration, velocity, part, measure), pitch in any scale of `transformAttributes`, time in seconds or beats, weights from velocity, ones, or duration, part selection, and chord binding (`'bind'`, the default, gathers notes that start together into one K > 1 event with NaN padding; `'separate'` gives one event per note). It feeds `buildMaet` or any pre-MAET preprocessor directly.

#### Per-level Möbius point evaluation of nested densities

- **`evalMaet(..., 'method', 'mobius')` / `eval_maet(method='mobius')` on a nested density** runs a per-level Möbius evaluator (`mobius.evalNestedAttrOrbit` / `_tensor/_nested_mobius_eval.py`). The nested density is a recursive construction over the tag tree; the evaluator applies the Möbius set-partition identity at every symmetric level (children in place of values), a dynamic programme at every ordered level, and, for a co-transposition unit at any level, the translation quadrature of the flat relative evaluator inside the recursion — one independent integral per block. It materialises no tuple centre, so its cost is polynomial in the values per event where the centres route's grows with the product of per-level factorials and binomials (at $r = (3, 3)$ over four groups of three, 5184 centres per event, it is several hundred times faster). It agrees with the centres route to the accuracy floor on every nested shape (any depth, symmetric or ordered levels, absolute or any unit, periodic under either `wrap`, ragged events, nested ⊗ flat), and honours `wrap`. Under `'auto'` nested densities take the centres route, the per-level route being selected with `'method', 'mobius'`.

#### `transformAttributes` / `transform_attributes`

- **Pre-MAET preprocessing helper.** Maps every value of selected attributes through a transform on the pre-MAET; weights pass through. Joins `differenceEvents`, `bindEvents`, `translateAttributes`, and `weightEvents` as the fifth pre-MAET primitive. Each attribute's entry is `[]` / `None` (unchanged), a **named transform** — `'log'` (`base`, default $e$; `offset`, default 0: $\log(x + \text{offset})$), `'power'` (`exponent`), `'affine'` (`scale`, `offset`) — a **pitch-scale conversion** given as a pair from `'hz'`, `'midi'`, `'cents'`, `'octave'`, `'mel'`, `'bark'`, `'erb'`, `'greenwood'`, or a **user function** on the $K_\text{total} \times N$ value matrix. A single entry broadcasts across attributes.
- **Absorbs `convertPitch` / `convert_pitch`.** The bare-array form `transformAttributes(f, [], {'hz', 'cents'})` / `transform_attributes(f, None, ('hz', 'cents'))` replaces `convertPitch(f, 'hz', 'cents')` / `convert_pitch(f, 'hz', 'cents')`, which are removed (see Removed). The seven v2.0 scales are unchanged; `'octave'` (MIDI / 12, sharing the MIDI origin) is new.
- **Domain refusals.** Values outside a transform's domain raise rather than propagate as $\pm\infty$ or `NaN`; the message names the attribute and events and lists the remedies. A zero under `'log'` — typically the inter-onset interval of a chord or grace note — points to `bindEvents`, deliberate dropping, or an explicit `offset` (`log(x + c)`, defined at zero but not unit-free, so the constant is written down rather than hidden).
- **Sign attribute.** `'sign', true` / `sign=True` (scalar or per-attribute) applies a magnitude transform to $|x|$ and inserts a sign attribute in $\{-\tfrac12, 0, +\tfrac12\}$ immediately after the source — the two signs are the vertices of the 2-point simplex at the toolbox's default unit edge length (`simplexVertices(2)` is $[+\tfrac12, -\tfrac12]$), with a zero step at the centroid, so the attribute sits on the same scale as any other categorical rather than at edge length 2 — extending `w` and `specs` (the source's spec with `rel` cleared and the name suffixed `'_sign'`). Insertion is explicit, never automatic, because it changes the attribute count that every downstream per-attribute argument is indexed by.
- **Composition with differencing.** `'log'` then `differenceEvents` gives log ratios; `differenceEvents` then a compressive transform with a sign attribute gives signed compressed magnitudes. Only `'affine'` is compatible with a periodic attribute at build.
- **Tests.** `test_transform_attributes.py` / `.m` replace the `convertPitch` tests and share a cross-language reference table.

#### Sequential-analysis utility

- **`continuity`.** Expected length and signed magnitude of the backward same-direction run leading up to each query, under Gaussian pitch uncertainty. Smoothed directional-agreement score $a_k = \mathrm{erf}(i_k/(2\sigma)) \cdot \mathrm{erf}(i_N/(2\sigma))$ drives a backward walk from the most recent context interval. Two break-threshold modes (`'strict'` with $\theta = 0$, `'lenient'` with $\theta = -1$) and an explicit-threshold override. Returns `(count, magnitude)`; `magnitude / count` is a trend-slope measure. An optional `w` argument supplies per-event salience weights; the salience of difference event $k$ is the rolling product $w_k \cdot w_{k+1}$, matching `differenceEvents` at order 1, and scales each interval's contribution to `count` and `magnitude`. Internally, the function routes through `differenceEvents` to compute both the context intervals and their weights, so the preprocessing is shared with the MAET-with-differencing pipeline; the read-out (a directional, order-preserving backward walk with a break condition) is not. Defined only on linearly ordered domains.


#### Categorical-encoding utility

- **`simplexVertices`** (MATLAB), **`simplex_vertices`** (Python). Returns the $N$ vertices of a regular $(N-1)$-simplex centred at the origin in $\mathbb{R}^{N-1}$, with all pairwise vertex distances equal to a specified `edgeLength` (default 1). Supports the simplex-coded encoding of an $N$-level categorical attribute (voice identity, instrument, etc.) for MAET inputs: each level is represented by an $(N-1)$-dimensional coordinate row, carried as one attribute read whole. All levels are pairwise equidistant, so no level is privileged over any other — in contrast to dummy or treatment coding. Construction uses the centred standard basis of $\mathbb{R}^N$ projected onto an orthonormal basis of $\mathbf{1}^\perp$; the result is rotation-equivalent across choices of basis, which is irrelevant for downstream MAET computations.

#### Soft (`sigma > 0`) structural measures

- **`sameness` / `coherence` — `sigma` argument with `sigmaSpace` flag.** Both functions now accept an optional positive `sigma` that softens the discrete equality / ordering tests against Gaussian positional uncertainty. With `sigma = 0` (default) the v2.0 hard counts are recovered byte-for-byte. With `sigma > 0`, `sameness` replaces each `[d1 = d2]` indicator with a Gaussian match kernel $\exp(-(d_2 - d_1)^2 / (2V))$, and `coherence` replaces each `[d2 \le d1]` indicator with the Gaussian-CDF probability $\Phi((d_1 - d_2)/\sqrt{V})$. The variance $V$ depends on the new `sigmaSpace` name-value flag: with `sigmaSpace = 'position'` (default), $V$ is computed per pair of intervals from the sharing structure of their endpoints (so the diatonic tritone, where the fourth and fifth share both endpoints with reinforcing signs, has $V = 8\sigma^2$ and the ordering test sees a tie at every $\sigma > 0$); with `sigmaSpace = 'interval'`, $V = 2\sigma^2$ uniformly (intervals treated as independent draws, ignoring index correlations). Float positions and float `period` are accepted when `sigma > 0`. See User Guide §12.7 (Scale and rhythm structure).

- **`nTupleEntropy` — `sigmaSpace` flag.** Adds a `sigmaSpace` name-value pair with the same semantics as `sameness` and `coherence`, governing whether the supplied `sigma` is treated as positional uncertainty on each event (the new default, `'position'`) or as independent uncertainty on each derived step (`'interval'`, matching v2.0 numerical behaviour). The `'position'` mode is the exact correlated model at every `n`: under positional uncertainty, adjacent first differences share an event, so the `n` steps of a tuple carry covariance $\sigma^2\,\mathrm{tridiag}(2, -1)$ (variance $2\sigma^2$ per step, $-\sigma^2$ between neighbours). The implementation binds the $n + 1$ underlying events and takes the bound window relative; the relative projection of the isotropic positional jitter onto the within-window difference space reproduces $\sigma^2\,\mathrm{tridiag}(2, -1)$ exactly from isotropic kernels, so no non-diagonal kernel covariance is needed. At $n = 1$ the value is reported on the relative-quotient grid, so `'position'` at $\sigma$ is not in general identical to `'interval'` at $\sigma\sqrt{2}$. `sigma = 0` gives the published integer-step histogram of Milne 2015bc / Milne & Dean 2016 under either flag. See User Guide §12.7.


#### Argand-DFT Monte Carlo

- **`dftCircularSimulate` / `dft_circular_simulate`.** Monte Carlo estimator of the distribution of Argand-DFT coefficient magnitudes under independent Gaussian positional jitter $\widetilde{p}_k = (p_k + \eta_k) \bmod P$, $\eta_k \sim \mathcal{N}(0, \sigma^2)$, where $P$ is the period. For each draw, the perturbed positions are sorted (capturing the perceptual reordering when noise is comparable to the smallest event-to-event gap), the Argand vector is formed, and the DFT is computed. Returns the per-coefficient mean and standard deviation of $|\widetilde{F}(k)|$ across draws by default; a third optional output (`samples` / `return_samples=True`) yields the full $n_{\text{draws}} \times K$ magnitude matrix for histogram or quantile analysis. Name-value parameters `nDraws` (default 10000) and `rngSeed` for reproducibility.

- **`balanceCircular`, `evennessCircular` — `sigma` argument.** Both functions now accept an optional positive `sigma` that triggers Monte Carlo estimation via `dftCircularSimulate` and returns the *expected* balance / evenness under positional jitter. At `sigma = 0` the v2.0 deterministic value is recovered exactly. The MATLAB versions also return the per-coefficient standard deviation as an optional second left-hand-side output (idiomatic `nargout`-driven multi-return); the Python versions accept a `return_std=True` flag that switches the return type from scalar to `(mean, std)` tuple. Backward-compatible at `sigma = 0` (scalar return preserved). Name-value `nDraws` and `rngSeed` are forwarded to the simulator. The augmented triad — perfectly balanced at `sigma = 0` — exhibits the expected Rayleigh-bias positive shift of $E[|F(0)|]$ at `sigma > 0`. See User Guide §12.6.

- **`projCentroid` — `sigma` argument (analytical closed form).** Because $y(x) = \mathrm{Re}(F(0) \cdot e^{-2\pi i x / P})$ is linear in $F(0)$ and $F(0)$ is permutation-invariant under positional jitter, no Monte Carlo is needed for the mean projection: $E[y(x)] = \alpha_1 \cdot y_{\text{deterministic}}(x)$ where $\alpha_1 = \exp(-2\pi^2 \sigma^2 / P^2)$ is the standard kernel-smoothing damping factor. Phase is preserved exactly in expectation, so `centPhase` is unchanged; `centMag` returns $\alpha_1 \cdot |F(0)| = |E[\widetilde{F}(0)]|$, the magnitude of the *complex mean centroid* — consistent with the projection. The distinct scalar $E[|\widetilde{F}(0)|]$ — the *mean centroid magnitude under jitter*, which picks up positive Rayleigh-style bias — is what `balanceCircular(p, w, period, sigma)` returns; the two answer different balance-related questions (see the `projCentroid` entry, User Guide §12.7).

#### Unified dispatch and consumer-level batching

A coherent strand of changes makes the consumer-facing entry points polymorphic on input shape and adds 2-D-pitch-matrix batching to most function families. The convention throughout: each row of a 2-D pitch matrix is one multiset, the $M$ rows form the batch, columns are slots, and NaN-padding allows variable-cardinality batches; weight matrices match the pitch-matrix shape. Every batched path uses canonical-form deduplication — symmetry-equivalent rows (permutation of slots, transposition modulo the period in `rel = true` modes, period-equivalence in `per = true` modes) are computed once per equivalence class and the result is mapped back to all matching rows. Which symmetries are exploited depends on what each function's output is actually invariant to (transposition-equivariant measures collapse only permutation and period-equivalence; transposition-invariant measures collapse all three). Name-value arguments such as `'spectrum'`, `'precision'`, and `'dedup'` are uniformly available across raw scalar and raw batched modes where they are meaningful. See User Guide §10.6 and §10.7 for the full convention.

- **`simMaet` / `sim_maet` — unified dispatch.** The function now accepts five input forms via type dispatch on its first argument: a single density struct (existing scalar path), raw arguments for a single multiset (existing scalar path), a cell array (MATLAB) or list (Python) of density structs (new "list mode" — returns a same-length cell / list of per-pair similarities), a 2-D pitch matrix with both dimensions > 1 (new "batched-raw mode" — rows are paired multisets, returns a length-`nRows` vector of similarities), and the MA cell-of-arrays raw form. The Option II shape rule applies to list mode: a length-1 list returns a length-1 cell / list, never a scalar. Backward compatibility is preserved exactly: every v2.0 calling form produces byte-identical results. Row-vector and column-vector inputs continue to dispatch to the existing scalar single-multiset raw path. The list and batched-raw modes are additive and mutually exclusive with the existing scalar dispatches based on input shape.

- **`evalMaet` / `eval_maet` — unified dispatch.** Five input forms via type dispatch on the first argument: a single density struct, raw arguments for a single multiset, a cell / list of density structs (returns same-length cell / list of per-density value vectors), a 2-D pitch matrix (rows are multisets, returns an `nRows`-by-`nQ` matrix of values; NaN-padded rows handled identically to `batchCosSimExpTens`), and the MA cell-of-arrays raw form. Option II shape rule applies in list mode. Backward compatibility is preserved exactly. In list mode, the `X` argument is broadcast to all densities by default; passing a length-`n` cell of per-density query matrices treats each entry as the `X` for the corresponding density (disambiguated by element type for single-multiset densities).

- **`entropyMaet` / `entropy_maet` — unified dispatch.** Symmetric additions to `simMaet` and `evalMaet`: list mode (cell / list of density structs returns cell / list of entropies, Option II shape rule) and batched-raw mode (2-D pitch matrix returns `nRows`-by-1 vector of entropies; NaN-padded rows handled; rows with fewer than `r` valid pitches return `NaN`). Name-value arguments (`'normalize'`, `'base'`, `'nPointsPerDim'`, `'xMin'`, `'xMax'`, `'gridLimit'`) are forwarded to per-row computations.

- **List-mode broadcasting.** Either operand of `simMaet` may be a single density struct paired with a cell array (MATLAB) or list (Python) of density structs; the single struct is broadcast against every entry of the cell / list, returning a 1-by-`n` cell / array of similarities (Option II shape rule preserved: a length-1 cell returns a length-1 cell). The pairwise and length-mismatch error paths are unchanged. The `'mode'` `'cartesian'` shape supported by Python `sim_maet` for full list × list cross-products is *not* part of MATLAB list mode; MATLAB list mode remains pairwise-only (with scalar broadcast as the single new shape).

- **Batched-raw broadcasting.** When one of `P1`, `P2` is an `M`-by-`K` matrix (`M > 1`) and the other is a vector of length `K` (1-D, `1`-by-`K` row, or `K`-by-`1` column in MATLAB; 1-D or `(1, K)` 2-D in Python), the vector is broadcast across the matrix's `M` rows in NumPy / MATLAB implicit-expansion style, and the corresponding weights argument is broadcast in lockstep when non-empty. Eliminates the `repmat(refPitches, M, 1)` / `np.tile(ref_pitches, (M, 1))` idiom for the common "compare one reference multiset against many candidates" use case. Mismatched row counts (when neither operand is broadcastable) raise `simMaet:rowMismatch` (MATLAB) or `ValueError` (Python) with a clear message. Backward compatibility is preserved: explicitly tiled `M`-by-`K` inputs continue to return byte-identical results.

- **`tensorHarmonicity`, `templateHarmonicity`, `virtualPitches` — batched-input dispatch.** Each function now accepts `p` as a 2-D `nRows`-by-`K` matrix with both dimensions > 1, treating each row as a separate multiset and returning per-row results. `tensorHarmonicity` returns an `nRows`-by-1 column vector of harmonicities. `templateHarmonicity` returns `hMax` and `hEntropy` each as an `nRows`-by-1 column vector. `virtualPitches` returns `vp_p` and `vp_w` each as a 1-by-`nRows` cell array of column vectors — cell-of-arrays output is used because the cross-correlation profile length varies per row (depending on the chord's pitch range plus margin), so a numeric matrix alignment is not natural. NaN-padded rows are accepted (NaN entries dropped per row, consistent with `batchCosSimExpTens`); rows with fewer than the minimum required valid pitches yield `NaN` (or empty cell entries for `virtualPitches`). The scalar (vector input) path is unchanged and produces byte-identical results to v2.0. The `p (:,1)` argument-block validation has been relaxed to `{mustBeNumeric}` to admit matrices; row vectors and column vectors continue to dispatch to the scalar path. Known limitations of the `templateHarmonicity` measures (interval-multiset symmetry of chord inversions; single-pitch / H1 hijacking at high spectrum-weight exponents; high-harmonic-density hijacking at low ρ with large N) apply equally to scalar and batched calls.

- **`spectralEntropy` / `spectral_entropy` — 2-D batched dispatch.** Argument shape relaxed to accept a 2-D `(M, K)` pitch matrix in addition to the original 1-D form. Rows are chords; the return is a length-`M` column vector of per-row entropies. NaN-padded rows are accepted (rows with no valid pitches return `NaN`). Per-row dedup uses the canonical-form key with `r=1`, `rel=true` (the function transposes internally), `per=false` — symmetry-equivalent inputs (transposed copies, permutations) share one cached entropy. Numerical results in scalar mode are unchanged.

- **Tier-1 batched dispatch (DFT-equivariant family): `dftCircular`, `meanOffset`, `edges`, `projCentroid`, `circApm`.** All five circular functions now accept a 2-D `(M, K)` pitch matrix in addition to their original 1-D form, and return 1-by-`M` cell arrays (MATLAB) / length-`M` lists of arrays (Python) for each output. NaN-padded rows are accepted; rows with no valid pitches give empty cell entries. Per-row dedup uses a canonical key built from sorted modular pitches plus matching weights, collapsing **permutation** and **period-equivalent** inputs onto one cached set of outputs. Dedup over **transposition is *not* applied** in this release — the DFT family is transposition-equivariant rather than invariant, and the per-output post-transforms required for full transposition dedup are non-trivial (especially for the query-grid functions whose outputs depend on user-supplied `x`); kept as a future optimisation. Weights may be `None`, the same shape as `P`, or a length-`K` vector broadcast across rows. For `circApm`, each `R` output is dense `period × period`, so memory scales as `M × period^2`; the docstring flags this and recommends chunked processing for large batches.

- **Tier-2 batched dispatch (structural functions): `coherence`, `sameness`, `nTupleEntropy`.** All three set-based circular functions now accept a 2-D `(M, K)` pitch matrix and return per-row results: length-`M` numeric vectors for scalar outputs (MATLAB column vectors / Python ndarrays), plus a length-`M` cell / list for `nTupleEntropy`'s variable-shape `tuples` output. NaN-padded rows are accepted; rows with no valid pitches give `NaN` in the scalar outputs and empty entries in the cell / list. These functions take no `w` argument (they're set-based and reject duplicates), so the batched signature has no weight handling. Per-row dedup keys differ across the three to match what each function's outputs are actually invariant to: `coherence` and `sameness` use the **necklace canonical form** of the cyclic adjacent intervals — collapsing permutation, period, and **transposition** symmetries onto a single cached result, since both functions are fully transposition-invariant on the circle in both `'position'` and `'interval'` modes. `nTupleEntropy` uses sorted-modular only (permutation + period); its `H` value is transposition-invariant but its `tuples` output reflects the input's cyclic ordering from sort-min and so differs across transposed inputs, which would break the dedup contract.

- **Tier-4 batched dispatch (Monte-Carlo functions): `balanceCircular`, `evennessCircular`.** Both functions now accept a 2-D `(M, K)` pitch matrix and return per-row `nRows`-by-1 column vectors (MATLAB) / length-`M` ndarrays (Python), with optional second output for per-row standard deviations. NaN-padded rows are accepted; rows with no valid pitches give `NaN` entries. New name-value pair `rngScope` (default `'canonical'`) controls how the per-row RNG seed is derived from the base `rngSeed` when `sigma > 0`: `'canonical'` derives each row's seed from the canonical-form key via FNV-1a hash, so canonical-form-equivalent rows share an identical Monte Carlo realisation and benefit from caching; `'row'` derives each row's seed from the row index, giving independent reproducible realisations per row and disabling caching. When `rngSeed` is empty, a session-random base seed is generated once per batched call so within-call dedup remains reproducible while across-call results differ. Per-row dedup uses sorted-modular canonical key (permutation + period). The same FNV-1a hash function is implemented identically in MATLAB and Python so a given canonical key produces the same derived seed in both languages.

#### Möbius method (and Bulger's method retained)

- **`method` keyword on `simMaet`, `evalMaet`, `entropyMaet`.** Accepts `'auto'` (default), `'bulger'` (the v2.0 inner-product decomposition; IP-only), `'mobius'` (the new partition-decomposition method, with orbit collapse applied in the IP case), `'centres'` (the unrestricted enumeration: the explicit centres-array path on `evalMaet`, and the reference route on `simMaet`), and `'contract'` (`simMaet` on a nested density). The `'auto'` setting routes on feasibility, the declared measure, and a per-call cost model that considers $r$, per-attribute $K_a$, event counts, and $\sigma/\text{period}$ for periodic-relative attributes; there is no timing probe, so identical workloads receive identical routing on every call and every machine. Backward compatibility: at default settings on standard inputs the dispatcher's chosen method produces v2.0-equivalent results to floating-point tolerance (a few ULP differences are possible where the cost model selects Möbius and the v2.0 route was Bulger, since the two are mathematically equivalent but accumulate in different orders).

- **`explainDispatch` / `explain_dispatch`.** Reports the route a call takes. On the flat cosine path it builds the selector's inputs by the same helper as the call and applies the same empty-operand and ordered-attribute rules, so its report agrees with the dispatch.

- **Pre-built orbit tables for $r \in \{2, \ldots, 8\}$.** Möbius coefficients, partition catalogues, and contraction edge lists are pre-built and shipped in both languages (Python `.pkl`, MATLAB `.mat`); at runtime the Möbius method looks up the table for the given $r$ and contracts, with no enumeration cost paid per call. The shipped maximum is exposed as `_ORBIT_R_MAX_SHIPPED = 8` (Python) and the matching `% _ORBIT_R_MAX_SHIPPED` boundary in MATLAB; the cost-model dispatcher consults it to route away from Möbius at $r > 8$ so users do not pay an unexpected on-demand build cost on first call. Wheel/sdist builds carry the seven shipped pickles via the new `[tool.setuptools.package-data]` block in `pyproject.toml`. Bell-number growth makes higher-$r$ tables expensive: $r = 8$ is 1.65 MB and roughly 3 minutes to build; $r = 9$ would be ~3 MB and ~80 minutes. Users wanting Möbius at $r > 8$ opt in by accepting the build cost on first call (subsequently cached on disk under `~/.mpt/orbit_tables/` or `MPT_CACHE_DIR`); a cost-preview helper prints estimated build time and Bell-number scaling context before the build begins, suppressible via `MPT_NO_BUILD_WARN=1`. A hard cap at $r = 12$ remains for the build path.

- **`+mobius` package (MATLAB) / `_mobius.py` module (Python).** Houses the Möbius-method implementation: `innerProductOrbit`, `innerProductOrbitPwBatched`, `innerProductOrbitGrid`, `evalOrbitAbs`, `evalOrbitRel`, `totalMassAbs`, `totalMassRel`, `getOrbitTable`, `buildOrbitTable`, `canonicalForm`, `contract`, and supporting partition / set-partition / contingency-table enumerators. All public-facing operations on densities continue to dispatch through the high-level wrappers (`simMaet`, `evalMaet`, etc.); the module is internal but documented for users wanting to understand or extend the machinery. (Internally the module's functions carry the label `'orbit'`; the user-facing API uses `method='mobius'`.)

- **Vectorised u-grid loop in `mobius.evalOrbitRel`.** The relative-mode evaluator integrates over the relative-coordinate axis $u$ (the translation parameter for relative-mode densities): a finite "u-grid" of $N_u$ sample points covers the support window, and the Möbius evaluator processes all u-grid points in a single chunked, batched call to `mobius.evalOrbitAbs`. `mobius.evalOrbitAbs` accepts query arrays of shape `(r, ...)` with arbitrary trailing dimensions; the trailing shape is preserved in the output. Per-block intermediate is `O(m_max · N · N_u · n_q_chunk)`, with chunking along the query axis to bound peak memory at a ~1 GB heuristic budget. Verified in `tests/test_orbit_vectorisation.{m,py}`.

- **Factored (K-free) integrand strategy in `mobius.evalOrbitRel`.** In non-periodic relative mode, each partition block's integrand factor at a u-node separates *exactly* as $\exp(-\mathrm{var}(\delta_B)/2\sigma^2)\, S_m(u + \mathrm{mean}(\delta_B))$, where $S_m(v) = \sum_i w_i^m \exp(-m(v - p_i)^2/2\sigma^2)$ is a query-independent smoothed event distribution at width $\sigma/\sqrt{m}$ and only $r$ distinct block sizes occur. The evaluator tabulates $S_1..S_r$ once (through `gaussianKernelSum`, so `truncation_sigmas` / `kernel_precision` apply uniformly) and reads them back by local quintic (6-point Lagrange) interpolation with a closed-form stencil shared verbatim between MATLAB and Python. Per-query cost is $B_r \cdot r \cdot N_u$ after the amortised tabulation, against $B_r \cdot r \cdot K \cdot N_u$ for the direct strategy. Read-back accuracy is governed by `truncation_sigmas`: the tabulation step targets a relative error at the kernel-truncation floor $\exp(-k^2/2)$, clamped to $[10^{-12}, 10^{-3}]$ (the factory default $k = 6$ targets about $1.5 \times 10^{-8}$, $k = \infty$ targets $10^{-12}$; `kernel_precision='single'` floors the target at $10^{-7}$). Error semantics match the rest of the Möbius machinery: read-back error is bounded relative to partition-*term* scales, so the assembled value's relative error degrades by the query's cancellation ratio (as reported by the cancellation-ratio diagnostic) exactly as truncation error and floating-point round-off already do on the direct strategy. A per-call cost gate selects the cheaper strategy (an internal switch the tests can force either way); in periodic relative mode the strategy applies where the variance/mean factorisation survives wrapping — the truncation window $\sqrt{2} k \sigma$ and each query's position span must both fit within half the period — and the direct strategy covers the remaining configurations, where a block's offsets can straddle an image boundary. The eval cost model prices the Möbius side as the cheaper of the two strategies, so batched relative workloads go to the factored strategy where it wins. Verified in `tests/test_orbit_rel_factored.py` and `tests/test_orbit_vectorisation.m`.

- **Spectral (Fourier) strategy in `mobius.evalOrbitRel`.** A third relative-mode strategy that carries no u-grid. Integrating the partition product over the translation $u$ forces the total mode index of each partition's per-block spectra to zero, so each partition reduces to a constrained coefficient of a product of per-block spectra, and the Fourier coefficients of a Gaussian mixture are available in closed form: $c_m[j] = (\sigma_m \sqrt{2\pi} / L) \exp(-2\pi^2 \sigma_m^2 j^2 / L^2) \sum_i w_i^m e^{-\mathrm{i}\omega j p_i}$, exact for the wrapped mixture on the period $L$. Evaluation dispatches by block count: single-block partitions are the analytic mass $\sum_i w_i^r \cdot \sigma\sqrt{2\pi/r}$; two-block partitions are one-dimensional mode series evaluated through a multiplicative phase ladder; partitions of three or more blocks are total-mode-zero coefficients obtained from cached per-block transforms, one per distinct block, shared across partitions exactly as blocks recur. The mode cutoff is set at machine precision (envelope $\exp(-8.6^2/2) \approx 8 \times 10^{-17}$) rather than at the requested accuracy floor, because the alternating partition sum amplifies per-term error by the query's cancellation ratio; since the mode count grows as $\sqrt{\log(1/\varepsilon)}$, machine precision costs about 16% more modes than the $10^{-12}$ floor would. The non-periodic case embeds in a virtual period padded to the truncation floor. Queries are chunked against the `kernelChunkBytes` budget; because the batched transforms differ in batch shape between chunkings, chunk invariance holds to machine precision rather than bitwise. `kernel_precision` does not apply: the coefficients are closed-form in double precision. The cost gate engages the strategy for $r = 2$, $3$, $4$ under `'auto'` above calibrated query-count and $K$ thresholds, and stands down for cancellation-ratio requests (the strategy has no per-node terms matching that diagnostic), outside the periodic validity window, and at $r = 5$, where the factored strategy remains faster at scale. Measured at $K = 300$, source span 3600, $\sigma = 15$, `truncation_sigmas=6`, non-periodic: at $r = 2$, 59 ms versus 1472 ms (direct) for 1000 queries; at $r = 3$, 805 ms versus 2578 ms; at $r = 4$, 1927 ms versus 5432 ms. Accuracy sits at the truncation floor throughout ($\le 1.3 \times 10^{-8}$ at `truncation_sigmas=6`, $\le 6.8 \times 10^{-13}$ at `inf`, over $r = 2\ldots5$ in both modes). The MA eval cost model prices the strategy with a span-aware per-query slope so that batched relative workloads are routed accordingly. Verified in `tests/test_orbit_rel_corr_r2.py` and the spectral-strategy block of `matlab/tests/test_mobius_eval.m`.

- **Spectral (Fourier) strategy for the relative-mode inner product.** The same partition-decomposition idea that removes the u-grid from `evalOrbitRel` also removes the translation grid from the relative-mode per-attribute inner matrix built by `_ma_per_attr_inner_matrix_rel`. Under a rigid diagonal shift the relative inner product integrates to the absolute one, and transforming along the shift constrains each partition's total mode index to zero, so each event carries a single spectrum $S_n(\xi) = \sum_\pi \mu(\pi) \prod_B A_{|B|}(\eta_B)$ with $A_m(\eta) = \sum_i w_{i,n}^m e^{-\mathrm{i}\eta p_{i,n}}$, and the matrix over event pairs is the Gram matrix of those spectra weighted by the envelope $\exp(-\sigma^2 \sum_s \xi_s^2)$ and scaled by $C_r = r \cdot (\sigma^2 \, d\xi)^{r-1}$. The K-dependence is paid once per event rather than once per pair; the per-pair cost is independent of K. Frequencies are exact on the circle (wrapped-Gaussian coefficients are closed form at any $\sigma/P$); on the line they are spaced $2\pi/L$ for an embedding period covering both sides' spans plus a truncation margin. Hermitian symmetry cuts the working sets in half on two sides: the envelope is even under $\xi \to -\xi$ and $S_n(-\xi) = \mathrm{conj}(S_n(\xi))$ for real Gaussian mixtures, so only the DC point plus one point per $(\xi, -\xi)$ pair is evaluated on the grid (off-DC envelope doubled to account for the conjugate partner); separately, real event weights give $A_m(-\eta) = \mathrm{conj}(A_m(\eta))$, so per-event phases are evaluated only on non-negative modes and the full $A_m$ table is assembled by reflection and conjugation. Measured combined speed-up is ~2× across $r = 2, 3, 4$ in both modes, with agreement to machine precision (max relative error $\sim 10^{-15}$). Gated onto `_ma_per_attr_inner_matrix_rel` for $r = 2, 3, 4$: the grid path costs $K^2$ per event pair while the branch costs the $(r-1)$-dimensional mode grid, so the branch is taken while the grid stays under $1000 \cdot K^2 \cdot n_x \cdot n_y$, plus a hard $4 \times 10^6$-point memory cap. Calibrated against measured wall times over $\sigma/P \in [0.0025, 0.05]$, $K \in [4, 100]$, and event counts 1 to 30; without the gate the small-$\sigma/P$ corner would run up to 12× slower than the grid path; with it, measured gains run from ~1.3× to ~1400× and no measured cell is slower. Verified against the grid path at $\sim 3 \times 10^{-13}$ across $r = 2, 3, 4$ in both periodic and non-periodic modes (absolute scale included, $C_r$ derived analytically with no fitted parameters). Both languages carry the branch (`internal.spectralIpEnabled` mirrors Python's `cosine._SPECTRAL_IP_ENABLED`, so tests can force the translation-grid route in either). Verified in `tests/test_spectral_rel_ip.py`.

#### Memoised self inner products, the `'oneSidedDenom'` $\langle X, X\rangle$ skip, and a direct all-$r = 1$ inner-product route

- **Self inner products are memoised on the density.** A cosine-similarity triple needs three inner products — the cross term $\langle X, Y\rangle$ and the two self terms $\langle X, X\rangle$, $\langle Y, Y\rangle$ — and the self terms depend only on their own density, whose contents never change after construction. Each density stores its self inner product on first computation and reuses it thereafter, keyed by everything the value depends on beyond the density itself: the decomposition route (the Bulger and Möbius conventions carry different constant prefactors that cancel only within a single route's triple), the resolved `truncationSigmas`, the kernel precision, and — on the Möbius route — the per-attribute closed-form-vs-grid choices, which alter the per-attribute prefactor. A sweep of many query densities against one context (`simMaet(densX, {d1, ..., dM})`) therefore pays the context's $O(N^2)$ self term once rather than $M$ times; the marginal cost per query is the $O(Nm)$ cross term plus the query's own small self term. In Python, `pruned` is memoised for the same reason: the similarity path prunes both operands per comparison, and returning one shared pruned object is what lets the memoised self term persist across a sweep. The dispatcher purges Möbius-route entries whenever its post-hoc impossible-value guard trips, so a rejected run never seeds the memo.

  The two languages realise the memo through their native semantics. Python attaches it to the (reference-semantics) density object, so it persists across separate calls automatically. MATLAB density structs are value types, so the memo there is carried by value: within one `simMaet` call the list loops thread it across pairs — which covers the list forms with no calling-convention change — and for a caller's own loop of scalar calls the density-struct scalar form offers optional cache-carrying outputs, `[s, densX, densY] = simMaet(densX, densY, ...)`, attaching the memo to the returned structs (a `selfIP` field) so the caller can thread the reference density through the loop. The extra outputs are refused with a clear error outside that form, where the internal threading already applies. The similarity values are identical in both languages and under either usage; the languages differ only in whether memoisation crosses call boundaries unaided.

- **`normalize='oneSidedDenom'` does not compute $\langle X, X\rangle$.** That normalisation's denominator is the second operand's self term alone, so the first operand's self term is not consumed; it is computed only when the `'cosine'` normalisation (or a memo hit, which is free) supplies a reason to have it. For the sweep shape above this removes the dominant term outright: at a 1,200-event context the per-offset cost of the benchmark configuration is under 1 ms, against ~42 ms with the self term computed, and the cost scales linearly in the context size, as the computed quantity implies.

- **Direct route for the all-$r = 1$ shape.** When every attribute has $r_a = 1$, each event contributes a single joint kernel and the inner product is a smoothed cross-correlation — the simplest shape the framework supports. A dedicated routine computes it with a single accumulator, in-place arithmetic, and a plain exponential, rather than through the generic multi-attribute path's per-attribute difference tensors and masked log-space exponential. The quantity computed is identical — same per-attribute terms in the same accumulation order, same truncation threshold including the summed-terms tightening, same chunking heuristic under `kernel_chunk_bytes` — and validation reproduces the generic path to the last bit across the absolute, periodic, and mixed mode combinations (relative attributes at $r_a = 1$ have a vanishing quadratic form and contribute nothing, exactly as the generic path evaluates them).

- **Point-set-shaped builds and sweeps are further specialised.** Two additions target the shape where each event carries one value per attribute at $r_a = 1$ (one note per event — the configuration a MAET offers in place of point-set query matching). First, the per-tuple field assembly recognises that shape directly: the perm- and comb-side arrays are the input value matrices themselves, the per-tuple weight is the product of the event's per-attribute weights, and the tuple index is the event index, so the general per-event, per-attribute enumeration machinery — which dominated the build cost of such densities — is bypassed, with field-for-field identical output (NaN-padded events fall through to the general path and its diagnostics). Second, a broadcast of one shared density against many queries of identical all-$r = 1$ geometry evaluates every cross inner product in a single batched kernel pass over the concatenated query columns, amortising the per-pair dispatch that otherwise dominates such sweeps; the truncation threshold is applied per column segment with each pair's own term count, so the set of zeroed kernel entries matches the per-pair path exactly, and self terms flow through the same memoisation keys, so subsequent per-pair calls see the same cache state. Any structural mismatch in the list bypasses the batched path and surfaces through the ordinary per-pair route with its usual diagnostics. Values agree with per-pair evaluation to the toolbox parity floor (the final contraction associates differently, a machine-epsilon effect); chunk width is additionally capped to a cache-resident block, since a single monolithic kernel block at large event counts leaves cache and forfeits the batched path's advantage. On the benchmark sweep configuration (1,200-event context, 3-event query, `'oneSidedDenom'`), repeated-minimum timing measures ~0.16 ms per offset in Python, within a small factor of a hand-written direct evaluation of the same quantity.

- **Cost models follow the computed work.** The pre-computation time estimate counts only the inner products the call will actually evaluate — memoised self terms and a skipped $\langle X, X\rangle$ are excluded — and the Bulger-vs-Möbius dispatcher's two pricing formulae accept per-route flags that exclude self matrices the call will not compute, so near-crossover routing reflects the marginal cost of each route rather than its full-triple cost.

#### Translation sweeps as a weighted Gaussian mixture in the offset

- **`sweepSimMaet` / `sweep_sim_maet`.** Compares one density against uniformly translated copies of another in one pass over the tuple pairs plus $M$ evaluations of a mixture in the offset, rather than one inner product per offset. The identity: on an absolute attribute the quadratic form separates as $Q_a(d - \mu_a \mathbf{1}) = r_a (\mu_a - \bar{d})^2 + \sum_i (d_i - \bar{d})^2$, where $\bar{d}$ is the mean of the tuple-pair difference. The second term does not depend on the offset, so each (tuple pair, attribute) contributes a fixed *shape* weight and a *placement* Gaussian in the offset, centred at $\bar{d}$ with effective width $\sigma_a / \sqrt{r_a}$. Placement and shape separate exactly. The integral of the profile recovers the relative-mode inner product, $\int \langle T_X, T_{Y + \mu} \rangle \, \mathrm{d}\mu = \langle T_X, T_Y \rangle_{\mathrm{rel}} \sqrt{4 \pi \sigma_a^2 / r_a}$, which is the same decomposition read in the other direction.

  Two properties make the reduction exact rather than approximate. The shape term is the *relative*-mode quadratic form, so it is computed as a Gram matrix of within-tuple-centred coordinates and no $r_a \times n_J \times n_K$ difference array is ever formed. And the truncation rule is the one the per-offset path applies, a floor on the accumulated log-kernel: because the placement term is non-positive, a component whose shape weight alone falls below the floor cannot rise above it at any offset, so dropping it before the sweep begins changes nothing. Both self inner products are invariant under a uniform translation of their own values, so each is computed once for the whole sweep rather than once per offset.

  Measured on a motif-in-passage sweep (400-event context, 8-event query, 360 offsets, two attributes, self terms warm): 36× at $K_{a,n} = r_a = 1$, 143× at $K_{a,n} = r_a = 3$, and 412× at $K_{a,n} = r_a = 4$ on a 120-event context. The saving is bounded by the offset count and erodes as the one-off mixture build comes to dominate, which is what the identity implies.

- **A second route for large tuple size, selected by `method`.** `method='mixture'` is the placement/shape split above; `method='orbit'` instead evaluates the Möbius/orbit inner product at the shifted values, with the (event pair, offset) index riding the orbit routine's batch axis, so its cost scales with $|\Omega_r|$ rather than with the tuple-pair count $[C(K_a, r_a) \, r_a!]^2$ that the mixture must both enumerate and store. `method='auto'` (the default) compares the two costs and picks. Measured on a single-attribute sweep at 180 offsets, the mixture leads by 22× at $(K_{a,n}, r_a) = (6, 4)$ and the orbit route by 16× at $(10, 4)$ and 33× at $(10, 5)$, with the crossover near 3 × 10⁶ tuple pairs. The two constants governing the choice are machine-specific in the same way as `orbitCostIntercept`; **`matlab/tools/calibrateSweepRoute.m`** measures them on a given machine and prints the values to use. Correctness does not depend on them, since either route computes the same quantity.

- **Attribute modes.** An attribute is handled by the split when it is flat or nested, non-periodic, and isotropic. Absolute contributes both a shape and a placement term; relative contributes the shape term alone, since the relative quadratic form *is* the shape term — a uniform translation cancels in every within-tuple difference, which is the same statement as having no placement term, and is why a relative attribute cannot be swept. A nested attribute resolved to an inner or intermediate co-transposition unit is that same case read per block: its form is the sum over blocks of each block's relative form, so it contributes one shape term per block, no placement term, and cannot be swept either. A periodic attribute that is never translated contributes an offset-independent factor through the same wrapped kernel the per-offset path applies; a *swept* periodic attribute is carried by the orbit route, which never forms the split and so is indifferent to periodicity. The orbit route is symmetric-only — the decomposition sums over unordered value subsets with multiplicity — so it declines an ordered attribute rather than silently symmetrising, and `'auto'` falls back to the mixture there.

- **Relative-and-periodic attributes** are never swept (a uniform translation is a no-op there) but may contribute their fixed factor. That factor is one of two measures — the single-wrap and the transposition-average kernel — which coincide only below a $\sigma / P$ limit, so the limit the inner-product dispatcher already calibrates governs acceptance: below it the two agree inside the floor `truncation_sigmas` implies, and no choice is being made silently. Above it the attribute's `wrap` decides, exactly as the per-offset dispatcher resolves the same question: `'single-image'` names the measure the mixture computes, `'full-image'` (the default) the one the orbit route computes.

#### Non-periodic quadratic forms as Gram matrices

- In every non-periodic mode the quadratic form is a squared Euclidean distance between (possibly quotiented) coordinates, so the shared multi-attribute log-kernel computes it as a Gram matrix, $\lVert u \rVert^2 + \lVert v \rVert^2 - 2 u \cdot v$, rather than as an $(r_a, n_J, n_K)$ difference array: absolute on the raw coordinates, relative on tuple-centred ones, nested on block-centred ones. Periodic attributes keep the difference path, where the wrap makes the form non-Euclidean. Measured on the log-kernel alone against the difference form: 2.1× at $r = 3$ absolute, 2.7× at $r = 3$ relative, and 3.4× at $r = 4$ relative with two attributes, with bit-identical values. The route serves multi-attribute work, since single-attribute inner products take the spatial-index helper rather than this routine.

- Both operands are shifted by one of the attribute's own values before the Gram matrix is formed. The identity cancels two large numbers when the coordinates sit far from the origin, which costs significant digits — measured against the difference form, the log-kernel departs by $4 \times 10^{-3}$ at coordinate magnitude $10^6$ and $5 \times 10^{-1}$ at $10^7$. Every quantity here depends on the operands only through their differences, so a shift shared by both is exact; taking it from the data rather than from a mean makes the subtraction itself exact as well (Sterbenz), where a mean would inject a rounding error at just those magnitudes. A guard compares the residual rounding, $\varepsilon s^2 / (4\sigma_a^2)$ for spread $s$, against the floor `truncation_sigmas` implies, and takes the difference form where the Gram form would not meet it — so a caller asking for accuracy-floor accuracy at small $\sigma_a$ gets the exact route and one asking for the default gets the fast one.

#### Kernel-evaluation controls (truncation and precision)

These controls govern how the dense Gaussian-kernel matrix is computed in the "centres path" — the path used by `evalMaet`, `simMaet`, and `entropyMaet` whenever the dispatcher selects the explicit-centres-array evaluation strategy (every $r$-tuple in the source cartesian product is materialised as a Gaussian centre, and each query point is evaluated by summing kernel contributions from all centres). The Möbius method evaluates the same density without forming the centres matrix. `truncation_sigmas` governs its accuracy too, in the inner product and in point evaluation (see the relative-mode note in the *Overview*); `kernel_precision` applies to its point evaluation, whose reduced kernel sums it casts, but not to its inner product.

- **`truncation_sigmas` (Python) / `truncationSigmas` (MATLAB).** Type `float`, default `6`. At the default $k = 6$, the Gaussian kernel contribution from each centre $\mathbf{c}$ to each query $\mathbf{x}$ is skipped whenever the Mahalanobis distance $\|\mathbf{x} - \mathbf{c}\|_Q$ exceeds $k \sigma$, equivalently whenever the kernel value drops below the floor $\exp(-k^2 / 2)$. ($Q$ is the kernel's inverse-covariance metric; for an isotropic Gaussian $Q = I/\sigma^2$ and the test reduces to $\|\mathbf{x} - \mathbf{c}\|_2 > k\sigma$.) The skip is implemented as a grid-bucket spatial index that avoids forming the dense kernel matrix for the discarded entries, saving the dominant `exp` and matrix-multiply cost on values that would round to negligible contributions anyway. Truncation perturbs the result by a small absolute amount bounded by the $k\sigma$ tail $\exp(-k^2/2)$: the worst-case error versus the exact result is about 1e-3 at $k = 4$, 1e-5 at $k = 5$, 2e-8 at the default $k = 6$, and 1e-10 at $k = 7$, reaching the cross-language 1e-12 parity floor by $k = 8$. This is an absolute error — on a cosine similarity directly, and on an evaluated density as a fraction of its scale — and is somewhat larger at large tuple size $r$, where more pairwise coordinates can sit near the truncation boundary at once; the relative error at query points deep in the tails is unbounded but falls on negligible-mass points that are never summed, integrated, or compared. Set `truncation_sigmas` / `truncationSigmas` to `math.inf` / `Inf` for the accuracy floor: it resolves to the finite width (about 7.43σ) at which the kernel falls below $10^{-12}$, the reference against which the toolbox's cross-language 1e-12 parity is verified; each added sigma shrinks the error by $\exp(-(2k+1)/2)$ at a cost that grows as $k^{r}$ with tuple size. Affects all centres-path consumers (eval, cos-sim, entropy), in the single-multiset corner and the general multi-attribute case alike.

- **`kernel_precision` (Python) / `kernelPrecision` (MATLAB).** Accepts `'double'` (default) or `'single'`, the latter casting the kernel-matrix arithmetic to `float32` for a ~2× speedup at the cost of approximately 7 significant figures of precision (vs approximately 15 for double). The cast applies only to the kernel matrix and its immediate matrix multiplication; density coordinates and the final summation in cosine / entropy are preserved at full double precision. Recommended for large-$K$ eval and centres-path cos-sim at scale, where the user is interested in similarities to three or four significant figures and the speed-up is substantial.

- **Toolbox-wide defaults.** A new defaults module exposes `mpt.set_default`, `mpt.get_default`, `mpt.get_defaults`, and `mpt.reset_defaults` in Python; MATLAB exposes the same functionality via `mptDefaults`: `mptDefaults` (no arguments) returns a struct of current values, `mptDefaults('name')` returns one value, `mptDefaults('name', value, ...)` sets one or more values and returns the previous values for save-and-restore idioms, `mptDefaults('reset')` returns to factory values. Per-call kwargs always override defaults. Defaults persist within a single Python process (not across processes) and within a MATLAB session (not across `clear all`). Factory defaults are `truncation_sigmas` / `truncationSigmas` $=$ `6`, `kernel_precision` / `kernelPrecision` $=$ `'double'`, and `show_hints` / `showHints` $=$ `True` (gates the toolbox's informational dispatch-decision messages; set to `false` to silence).

#### Rényi-2 differential entropy

- **`method='renyi2'` on `entropyMaet` / `entropy_maet`.** Computes $H_2 = -\log_b(\langle T, T\rangle / Z^2)$ in closed form via the Möbius method's inner product for $\langle T, T\rangle$ and the Möbius method's total mass for $Z$. The inner product goes through the same per-attribute IP matrix as `simMaet`, and the total mass through `mobius.totalMassAbs` / `mobius.totalMassRel`; a multi-attribute density factorises $\langle T, T\rangle = \sum_n \prod_a I_a^{(n,n)}$ via the per-attribute IP matrix and likewise use a per-event total-mass product for $Z$. The default remains `method='shannon'` (numerical Shannon entropy on a discretised grid), so existing callers see no behavioural change. `r=1` rel returns 0 by convention (0-D relative space; constant density); a zero-mass density (every weight zero, or a window with no event in support) returns `NaN`, its collision entropy being undefined; `r=1` abs uses a direct kernel-sum branch since the orbit table is undefined at $r=1$.

#### Four-method entropy API and adaptive differential entropy

- **`method='differential'` on `entropyMaet` / `entropy_maet`.** Adaptive nested-grid evaluation of the differential entropy $\hat h = H_\text{disc} + \log_b(\Delta\text{-volume})$, the grid-independent continuous quantity that compares densities of different cardinality or spread on the same scale (unlike normalised Shannon, which is grid-dependent). The span auto-derives per attribute from `centres ± truncation_sigmas * sigma` (non-periodic) or `[0, period]` (periodic); the grid doubles from a sample-per-sigma initial resolution until successive Richardson-extrapolated estimates fall below tolerance, anchored at $\max(\exp(-\text{truncation\_sigmas}^2 / 2), 10^{-12})$. Richardson extrapolation upgrades the bin-integration's $O(\Delta^2)$ rate to $O(\Delta^4)$, making multi-dimensional convergence feasible without exhausting `grid_limit`. Errors at `sigma=0` (the continuous form diverges). Currently restricted to single-density input (scalar density, raw scalar single-multiset or multi-attribute form); list and batched input forms raise `NotImplementedError`. Bin-integration core via per-axis Φ-difference contractions is shared with the discrete methods, so the same density paths are exercised.

- **`method='normalized'` (alias `'normalised'`) on `entropyMaet` / `entropy_maet`.** Explicit name for the Pielou-style ratio $H / \log_b(N)$ in $[0, 1]$. Equivalent to v2.0's `normalize=True`, and reproduces the values reported in Milne et al. (2017) and Smit et al. (2019). Accepts the British spelling as an alias via `_canonicalize_method`.

- **`σ=0` guards on continuous methods.** Both `method='differential'` and `method='renyi2'` error at `sigma=0` with an informative message pointing users to `method='shannon'` or `method='normalized'` for categorical entropy. The guard reads sigma from the density object (`MaetDensity`) or the raw input.

#### Matrix-valued kernel covariances (anisotropic kernels)

- **`sigma` accepts an $r \times r$ covariance matrix.** On an ordered (`exch = false`), absolute (`rel = false`), non-periodic (`per = false`), non-nested attribute whose tuple is its whole multiset ($r = K$), the per-attribute `sigma` of `buildMaet`, `evalMaet`, `simMaet`, `entropyMaet` (all four methods), `sweptSimilarity`, and `sweptEntropy` may be a symmetric positive-definite matrix $\Sigma$ instead of a scalar: the Gaussian kernel becomes $\exp(-\delta^{\top} \Sigma^{-1} \delta / 2)$, and the inner product of two densities sharing $\Sigma$ depends on centre differences through $\exp(-\delta^{\top} \Sigma^{-1} \delta / 4)$. A scalar `sigma` remains a standard deviation; a matrix is the covariance (squared units). Validation always errors: a non-square, wrongly sized, asymmetric, non-finite, or non-positive-definite matrix raises (one attempted Cholesky factorization is the definiteness test), as does a matrix supplied on a symmetric, relative, periodic, nested, or $r < K$ attribute, on `'spectrum'` input, or on values containing NaN pads. Exact common-shift invariance remains the province of `rel = true` — a matrix covariance expresses its graded counterpart, and an infinite shift variance is rejected rather than approximated.

- **Whitening implementation.** With the Cholesky factorization $\Sigma = R R^{\top}$, values and query points are transformed once by $R^{-1}$ and every downstream computation (density evaluation, inner products, entropies, truncation and precision controls) runs unchanged on whitened coordinates at unit `sigma`. The Gaussian normalisation constant acquires $\det(\Sigma)^{-1/2}$ (`normalize = 'gaussian'` / `'pdf'`; it cancels in cosine similarity), and the continuous entropies acquire the additive change-of-variables constant $\tfrac{1}{2} \log \det(\Sigma)$. Inner products require the same covariance on both operands (per attribute); a mismatch raises.

- **`kernelCov` / `kernel_cov`.** Constructor for the kernel covariance of an ordered tuple from three sources of variance, each included only when its width is set: independent noise on the values themselves (`sdValue`), independent noise on the intervals between consecutive values (`sdInterval`), and a common shift of the whole tuple (`sdShift`). A mandatory `differenced` flag says how the three reach the tuple. With $\nabla$ the first-differencing map, taken at the size its operand requires ($(r - 1) \times r$ on a tuple of $r$ values, $r \times (r + 1)$ on a tuple of $r$ differences), and $\nabla^{+}$ its pseudoinverse: on undifferenced values $\Sigma = \mathrm{sd\_value}^2 \, I + \mathrm{sd\_interval}^2 \, \nabla^{+}(\nabla^{+})^{\top} + \mathrm{sd\_shift}^2 \, \mathbf{1}\mathbf{1}^{\top}$, the interval noise accumulating as a random walk centred on the tuple's mean; on first-differenced values $\Sigma = \mathrm{sd\_value}^2 \, \nabla\nabla^{\top} + \mathrm{sd\_interval}^2 \, I + \mathrm{sd\_shift}^2 \, \mathbf{1}\mathbf{1}^{\top}$, the value noise reaching each interval through its shared endpoints ($\nabla\nabla^{\top}$ tridiagonal, $2$ / $-1$). The two are one model, differencing a tuple of $r$ values carrying the first to the second at tuple size $r - 1$. The ridge tolerates a common shift by degree, `rel = true` being its exact limit: a transposition or displacement on undifferenced values, a common factor (tempo, augmentation) on log-differenced intervals. On times, value and interval noise are the two levels of the Wing & Kristofferson (1973) model (`sigmaSpace = 'position'` / `'interval'` in `nTupleEntropy`). All widths are standard deviations in the attribute's own coordinates, squared internally; combinations that are not positive-definite raise (on undifferenced values positive-definiteness needs `sdValue` > 0, or `sdInterval` and `sdShift` both non-zero; on differenced values `sdValue` > 0 or `sdInterval` > 0), and $r = 1$ is rejected in both languages because a $1 \times 1$ covariance is indistinguishable from a scalar `sigma` in MATLAB.

- **`exch` on `sweptSimilarity` / `sweptEntropy`.** New keyword carrying the per-attribute symmetry vector of the flat surface through the sweep's internal builds and comparisons (`None` / omitted keeps the unordered default). Required, in particular, for ordered attributes carrying a matrix-valued kernel covariance. Mutually exclusive with `specs`, whose nesting carries its own per-level exch.

- **Degenerate nested attributes accepted (and flattened).** A matrix-valued kernel covariance is accepted on a nested attribute when the nesting is *degenerate* --- two levels, every group a singleton read whole, inner level absolute, outer level reading all groups --- the form produced by `bindEvents` / `bind_events` over flat single-slot events. Such an attribute is order-isomorphic to the flat ordered tuple over the same value matrix (identical densities), so the `specs` build path flattens it automatically before whitening (`internal.flattenDegenerateNestedSpec` / `flatten_degenerate_nested_spec`); outer-level `exch` / `rel` flags carry through to the standard mode-constraint checks and are rejected with the canonical messages. A matrix sigma on a *flat* spec passed via `specs` is likewise accepted, matching the positional form. An all-scalar cell `sigma` in the MATLAB `specs` form is coerced to numeric, likewise mirroring the positional path. Non-degenerate nesting on a matrix-sigma attribute errors. `demos/demo_tempoInvariance` / `demos/demo_tempo_invariance` builds its trigram pre-MAET this way (`differenceEvents` then `bindEvents`), expressing the rel kernel via `relOuter = true` --- the spec-native form of the common-shift quotient.

#### `normalize` NV on `simMaet`

- **`normalize` / `normalise` keyword.** Two values, `'cosine'` and `'oneSidedDenom'`, case-insensitive on the value; both spellings of the keyword name are accepted. The default is `'cosine'` — the strict shape-only cosine similarity $\langle X, Y \rangle / \sqrt{\langle X, X \rangle \langle Y, Y \rangle}$, bounded in $[-1, 1]$ and invariant to positive scalars on either operand. `simMaet(..., 'normalize', 'oneSidedDenom')` divides by the second operand's self inner product alone — a magnitude-aware reading sensitive to scalar rescalings of the first operand, and the default that `sweptSimilarity` / `swept_similarity` passes through for its sliding comparison (self-similarity at full window coverage equals 1, with an unbounded range above); `sweptSimilarity(..., 'normalize', 'cosine')` gives the strict shape-only cosine for the windowed comparison. See User Guide §8.3 and §8.7.

#### `maetCentres` / `maet_centres`

- **A public accessor for a density's tuple centres.** `buildMaet` defaults to `'lazy', true` and returns a density whose per-tuple fields are not yet built, so a density that reached its consumer by the Möbius route carries no `Centres` array at all. `maetCentres(dens)` / `mpt.maet_centres(dens)` is the supported way to ask for one: it materialises the fields when they are absent, passes them through when they are not, and returns a cell / list of one `(r_a - isRel_a)`-by-`nJ` matrix per attribute, in that attribute's own coordinates and unwrapped on a periodic attribute.

#### `massMaet` / `mass_maet` and `sweptMass` / `swept_mass`

- **The total mass of a density.** `massMaet` takes each tuple's kernel with unit mass and returns the density's total mass, the sum of its tuples' weight products, $M = \sum_j w_j$ (the integral of what `evalMaet` returns under `'gaussian'`); where every weight is 1 it is the number of tuples. The density factors across attributes within each event, so the joint tuple set is never built. Its use is as a normalizer: a one-sided similarity (`'oneSidedDenom'`) of a context with a query counts, in units of the query, the context's tuples that match it, and the query's mass over the context's turns that count into their share of the context's tuples (`demo_overview`, parts 1d and 2d).
- **`sweptMass`**, the swept counterpart, takes the arguments of `sweptEntropy` and at each sweep value takes the total mass of the windowed density: how much material the window holds, the normalizer of a windowed one-sided similarity.
- **The swept functions return their sweep values.** `sweptSimilarity` gains a third output and `sweptEntropy` and `sweptMass` a second, `sv`: the sweep values of each swept attribute, listed or generated, as a 1 x A cell (Python: `return_sweep_values=True`, a dict `{a: values}`; under `'independent'` the pair of the window's list and the query's). They are the axes of the profile, so a sweep whose values were generated from the defaults or from `'start'`, `'stop'`, and `'step'` can be plotted directly; the offsets `mu` equal them only under `'query'`. Tests: `test_swept_sweep_values.py` / `.m`.
- **`sweptEntropy` takes the grid of the discrete methods.** `'nPointsPerDim'`, `'xMin'`, `'xMax'`, and `'gridLimit'` (Python `n_points_per_dim`, `x_min`, `x_max`, `grid_limit`) are passed to `entropyMaet` at every sweep value, so `'shannon'` and `'normalized'` profiles are taken on one grid throughout. Tests: `test_swept_premaet.py` / `.m`.
- **A zero-mass density has undefined entropy under every method.** `entropyMaet` returns `NaN` for a density whose weights are all zero, or a window with no event in its support, under `'shannon'`, `'normalized'`, and `'differential'` as under `'renyi2'`, so an empty window reads as missing in every entropy profile.
- Pinned to the density's tuple weights, to hand-computed weight sums, to the `weightEvents` → `buildMaet` → `massMaet` composition, and to the share of the diatonic scale's pairs a fifth or fourth apart (6 of 21) in `test_mass_maet.py` / `test_massMaet.m`.

#### The batched-raw shape rule is documented as a deliberate divergence

- **MATLAB and Python enter batched-raw mode by different rules, and say so.** MATLAB enters it on an operand that is a matrix with both dimensions greater than one, so a `K`-by-1 column is a vector and is broadcast as one multiset shared by every row; Python enters it on `ndim == 2`, so a `(K, 1)` array is `K` rows of one element each. Each rule is the idiomatic one in its own language, so both are kept; the divergence is stated in the docstrings of `simMaet` / `sim_maet`, `evalMaet` / `eval_maet` and `entropyMaet` / `entropy_maet`, in User Guide §10.6 and in ARCHITECTURE §7, and pinned by `test_batched_shape_rule.m` / `.py`. A batch of one-element multisets – a probe-tone sweep, say – is written the same way in both languages: pad to two columns with NaN, the padding being stripped per row before each density is built.

#### Demo: handling repeated pitches under interval-scale and tempo invariance

- **`demos/demo_repetitionHandling` / `demos/demo_repetition_handling`.** Matching a melodic contour up to a uniform scaling of its intervals carries each pitch step as two attributes --- sign, and the logarithm of the step magnitude, the bound log-magnitude tuple read relative (`relOuter`) so a common scaling becomes a quotiented common shift. A repeated pitch has step 0, which has no logarithm, so something must be done with repetitions first, and the demo walks the same melody (the Ode to Joy opening, whose repetitions are non-uniformly placed) through the three treatments: *excise* (drop each zero-step event with its inter-onset interval; a repetition leaves no trace, so the melody is identified with its repetition-free, closed-up form), *prolong* (gather each run of equal consecutive pitches into one event before differencing; the repetition survives as duration, at the cost of identifying a re-articulated note with a held one), and *count* (prolong, plus a per-event attribute holding the number of gathered onsets; re-articulation survives as such, and its sigma grades the distinction back toward the prolong identification as it widens). Each treatment runs twice --- inter-onset intervals in beats (tempo-sensitive) and log inter-onset intervals read relative (tempo-invariant) --- and the invariant run exposes the confound the sensitive one hides: where repetition is uniform (every note repeated equally), closing the repetitions up *is* a tempo change, and only the count attribute, dimensionless and so invariant to both scalings for free, keeps the two apart. Exact quotients only (`relOuter` flags); the graded counterparts (the `sdShift` ridge of `kernelCov`, tending to rel in the limit) are the subject of `demo_tempoInvariance`.

### Changed

#### The flags are named `rel`, `per`, and `exch` (breaking)

The three flags take the names the article gives them, [rel], [per], and [exch], wherever they are named: the density's fields (`dens.rel`, `dens.per`, `dens.exch`), the spec fields, and every name-value argument and keyword. v2.0 named the density's fields `isRel` / `is_rel` and `isPer` / `is_per`. Calls that pass the flags by position are unaffected. MIGRATION.md has the mapping.

#### Periodic kernels sum every periodic image (`wrap`)

- **A periodic attribute's kernel sums every periodic image the truncation admits.** Under the default `wrap='full-image'` each periodic attribute's kernel — in point evaluation, inner products, and the Shannon and normalized entropies' cell masses — sums the contributions of every periodic image within the truncation width, where v2.0 wrapped each difference to a single image. Values differ from the single-image ones only where σ/period is large (for the entropies, above about 0.06); `wrap='single-image'` gives the single-image kernel. Two operands declaring different `wrap` on the same attribute are refused (`ValueError` / `mpt:wrapMismatch`).

#### Discrete entropy integrates each cell's mass

- **`method='shannon'` and `method='normalized'` integrate the density over each grid cell** (per-axis erf differences) for absolute-mode densities, rather than point-sampling it at the cell centres as v2.0 did; the two converge as the grid is refined but differ at coarse-to-moderate resolution (~$10^{-2}$ at 2.6 samples per σ, ~$10^{-5}$ at 12). The integration is identical in the two languages to machine precision, and the MATLAB contraction chunks its source-tuple axis to bound memory. Relative-mode densities are point-evaluated, as before.

#### Default kernel truncation is `6` (breaking numerical change)

- **`truncation_sigmas` / `truncationSigmas` factory default is `6`.** Default-configured output from every centres-path consumer (`evalMaet`, `simMaet` on Bulger's method, `entropyMaet`, `spectralEntropy`, `templateHarmonicity`, `virtualPitches`) is therefore a ~6-significant-figure approximation of the untruncated result rather than bit-identical to v2.0. The worst-case relative error (~$10^{-6}$ to $10^{-7}$ for `centres`, smaller for the Möbius realisation) falls at low-density query points; near the density's bulk it is far smaller, and for the perceptual-modelling regimes the toolbox targets the approximation is well below any perceptually or statistically meaningful threshold. The change is motivated purely by speed: the grid-bucket truncation is a large win (tens to >100× over the untruncated path at large $K$ in the pruning regime), and `6` sits near the knee of the speed/accuracy curve, where the retained-neighbour count scaling as $k^{r}$ means smaller $k$ is materially faster at larger tuple size. **To recover the v2.0 numerics to within $10^{-12}$**, set `truncation_sigmas` / `truncationSigmas` to `math.inf` / `Inf`, which resolves to the accuracy floor (about 7.43σ) — per call, or globally via the defaults API. Cross-language Python↔MATLAB parity is verified at $\le 10^{-12}$ at that floor; the default path is deterministic and identical across languages, so parity is preserved there too, only against the truncated value rather than the untruncated one.

- **A first-use truncation notice.** The toolbox issues a one-time-per-session warning the first time a kernel evaluation resolves the truncation default at its factory value of 6 — giving the worst-case error versus the exact result at 4, 5, and 6 sigma (about ~1e-3, ~1e-5, and ~2e-8 respectively) and pointing to `truncation_sigmas=inf` for exact output. It fires from the defaults getter (`mptDefaults('truncationSigmas')` / `get_default('truncation_sigmas')`), through which every kernel-evaluating path resolves the default, so it appears on first use regardless of which function the script calls. It is issued as a warning (identifier `mpt:truncationDefault` in MATLAB, category `mpt.TruncationDefaultWarning` in Python) so it goes to stderr and is suppressible through the standard warning machinery. It is deliberately **not** gated by `show_hints` / `showHints` — it always gets its single showing — and it stays silent after that first showing, once the user sets an explicit truncation value, or throughout the test suite. The `show_hints` / `showHints` flag governs only the toolbox's dispatch-decision messages.

- **The toolbox-wide default of `n_points_per_dim=1200` has been dropped** to `None` in `entropy_maet`. `method='shannon'` and `method='normalized'` now require the caller to pass an explicit grid resolution; a missing value raises `TypeError` with a message pointing to either supplying `n_points_per_dim` or switching to a grid-free method (`'differential'` or `'renyi2'`). The previous silent default masked grid-fragility bugs — the right grid resolution is density- and sigma-dependent — and forcing the choice up front protects callers from accidentally relying on a value tuned for a different regime. The check fires after input-form validation, so the more-specific "extra positional", "spectrum with density", and "precision with density" errors continue to surface when both apply. The check is bypassed by the continuous methods (`differential` adapts its own grid, `renyi2` is analytical).

#### `spectralEntropy` / `spectral_entropy` default method (breaking semantic change)

- **`spectralEntropy` / `spectral_entropy` default switched from `method='shannon'` (with `normalize=True`) to `method='differential'`.** The new default returns the adaptive differential entropy $\hat h$ — a different quantity in different units, not a fourth-decimal numerical shift. The previous default behaviour is recovered by passing `method='normalized'`, which computes on the grid the published method used, `0 : resolution : max(spec_p) + 4σ` with `resolution=1` cent by default (the spacing is exposed as a keyword, since a discrete entropy depends on its grid); the values agree with Milne et al. 2017 and Smit et al. 2019 to about 1e-4, the difference between the cell masses the v3 discrete entropy integrates and the point samples v2.0 summed. `method` is canonicalised at the public entry point (accepting `'normalised'` as alias).

#### `nTupleEntropy` / `n_tuple_entropy`: thin wrapper, `method` kwarg, and `sigmaSpace` semantics

- **`nTupleEntropy` / `n_tuple_entropy` refactored as a thin wrapper.** Internally now calls the `differenceEvents` $\to$ `bindEvents` $\to$ `buildMaet` $\to$ `entropyMaet` pipeline. With default arguments (`sigma = 0`, `nPointsPerDim = period`, `method = 'normalized'`) it exactly replicates the discrete n-tuple entropy of Milne & Dean (2016) byte-for-byte; existing call sites at `sigma = 0` are unaffected. New optional name-value pairs expose the underlying flexibility: `nPointsPerDim` controls the entropy-evaluation grid resolution per dimension (the integer-step grid by default, finer for better resolution of smoothed densities). For non-integer values, weighted events, non-periodic domains, or to obtain the n-tuple density itself for similarity comparison and other MAET operations, call the primitives directly. **Numerical change at `sigma > 0`.** As described above under *Soft (`sigma > 0`) structural measures*, the new `sigmaSpace` flag changes the default semantics of `sigma` at `sigma > 0`: the default `sigmaSpace = 'position'` treats `sigma` as positional uncertainty on each event, with the exact correlated covariance $\sigma^2\,\mathrm{tridiag}(2, -1)$ across the tuple's steps. v2.0's effective semantics treated `sigma` as independent per-step uncertainty, equivalent to `sigmaSpace = 'interval'`. The two coincide at `sigma = 0`. To recover v2.0 numerical results at `sigma > 0`, pass `sigmaSpace = 'interval'`. See [MIGRATION.md](MIGRATION.md) for a worked example.

- **`nTupleEntropy` / `n_tuple_entropy` gains a `method` kwarg** defaulting to `'normalized'`. The full four-method API is exposed; `'normalised'` is accepted as alias. It also takes `verbose`. The previous `normalize=True/False` boolean kwarg has been **removed**; v2.0 callers passing `normalize=False` should now pass `method='shannon'`, and callers passing `normalize=True` (the v2.0 default) get the same value without changes. The continuous methods (`'differential'`, `'renyi2'`) are rejected at `sigma=0` with an explicit error before the σ=0 → σ=10⁻¹² internal nudge that supports the categorical Gaussian-confusion path on a pinned integer grid.

#### `tensorHarmonicity` Möbius-method rewrite

- **`tensorHarmonicity` bypasses the density build.** Routes through `mobius.evalOrbitRel` (the Möbius method's relative-mode evaluator) for the harmonic-template tensor, with per-chord and per-template caching in batched mode (via `containers.Map` in MATLAB / `dict` in Python). No density object is constructed and no centres array is materialised. Output is unchanged from v2.0 at the floating-point level. The Möbius method handles any template size without the centres-array memory footprint.

- **`tensorHarmonicity` batched mode deduplicates and batches.** Pass 1 computes per-row metadata (`nP`, `dup`, canonical chord key, interval vector) and identifies valid rows; pass 2 groups valid rows by `(nP, dup)`, deduplicates canonical chords within each group, and issues a single batched call to the Möbius relative-mode evaluator per group. Batched and scalar modes share one floating-point path, so batched values match scalar values to machine precision by construction; for typical uniform-cardinality batches the loop collapses to a single Möbius-method call. The verbose-mode estimate is printed only for 100 rows or more, matching the `min_print_sec=10` semantics of the other batched functions.

#### Lazy density-struct in `buildMaet`

- **`buildMaet` defaults to lazy density construction.** The `lazy` keyword (default `true`) controls whether the expensive density fields (`U_perm`, `wJ`, `V_comb`, `wV_comb`) are materialised at build time. v2.0 always materialised them; v3 builds a "skinny" density struct and defers the expensive fields until a consumer needs them. Most consumers (Möbius-method cosine, eval, entropy) do not need the fields and benefit from the deferral. Consumers that do need the fields (Bulger's method, the centres-array eval) materialise them (idempotently) before reading; this is wired internally throughout the toolbox, and `maetCentres` exposes it. End-user behaviour is unchanged at the API level. `r = 1` with `rel = true`, which v2.0 refused at build (a relative density needed $r \ge 2$), now builds with a warning (`buildMaet:relDegenerate`), since it has a well-defined treatment (a constant 0-D space, total mass $\sum w$, Rényi-2 entropy 0).

#### Console output for batched calls: dispatch announces, cost estimates, and adaptive countdowns

Several user-facing console-output behaviours unified across the five batched-input helpers (`simMaet`, `templateHarmonicity`, `spectralEntropy`, `virtualPitches`, `entropyMaet`) so each long-running call emits a consistent, lightly-throttled trace: one dispatch announce per top-level user call, an empirical cost estimate when total runtime is expected to exceed ~10 s, and an adaptive row-count countdown when total runtime is expected to exceed ~5 s. All three pieces are present in both languages with matching semantics; verbose-gating (per-call) and `showHints`-gating (toolbox-wide) are decoupled in both languages. See USER_GUIDE.md §11.4 ("Messages") for the user-facing description, and ARCHITECTURE §6 for the thresholds.

- **Dispatch announces are throttled per top-level user call.** Each top-level toolbox entry opens a dispatch scope (`matlab/+internal/dispatchScope.m`; Python `_dispatch_scope` in `_defaults.py`, a thread-local, depth-counted, re-entrant context manager). Nested toolbox calls within a single top-level user call share a seen-set, so a batched-raw loop produces one announce per unique dispatch rather than one per item; successive top-level calls each re-announce. Public entry points wrap their bodies via `@_with_dispatch_scope` (Python) or the scope-acquire pattern (MATLAB).

- **Dispatch-announce message format and throttle key.** Messages read `simMaet: chose 'bulger' path.`. The throttle key is `(function, chosen)`, so two different routing reasons leading to the same chosen path within one top-level call collapse to a single announce. Neither the key nor the message carries the routing reason: the visible distinction that matters is which path ran, not why.

- **Adaptive countdown.** Replaces v2.0's fixed "every 100 rows" cadence with an adaptive stride chosen from the empirical calibration. New helpers `matlab/+internal/progressStride.m` and `python/mpt/_utils.py:progress_stride` pick the smallest "nice" stride from `{1, 2, 5, 10, 20, 50, 100, 200, 500, 1000, 2000, 5000, 10000}` such that each print interval takes at least 5 s at the calibrated per-row cost (so 1 ms/row → stride 5000; 1 s/row → stride 5; 10 s/row → stride 1, i.e. print every row). Combined with a `showProgress = (estTotal >= 5)` gate set inside each helper's calibration block, this means: extrapolated total runtime under 5 s → silent regardless of row count; runtime over 5 s → progress at the adaptive stride plus a final flush. No more hardcoded 100-row floor. The per-iteration check is uniform across all five MATLAB and four Python batched helpers: `verbose && showProgress && (mod(k, progStride) == 0 || k == nRows)`. The unit reported is `unique pairs computed` for `simMaet` and `rows computed` for the others.

- **Demos updated.** `demo_genChainPcs.m`, `demo_gen_chain_pcs.py`, and `demo_edo_approx.py` now pass `verbose=true` to their long-running batched `simMaet` call so the estimate and countdown surface on the slow sweep, matching the MATLAB `demo_edoApprox.m` counterpart. `demo_triadConsonance.m` / `demo_triad_consonance.py` already used `verbose=true`; `demo_triadSpcsGrid.{m,py}` deliberately stay silent (consistent with their MATLAB counterpart).

- **Demo rename and relabelling: SPCS → PCS where there is no spectral enrichment.** `demo_genChainSpcs.m` is renamed to `demo_genChainPcs.m` (and its Python counterpart `demo_gen_chain_spcs.py` to `demo_gen_chain_pcs.py`), and all "SPCS" and "spectral pitch class similarity" labelling in both these demos and in `demo_edoApprox.m` / `demo_edo_approx.py` is corrected to "PCS" / "pitch class similarity". These demos compute cosine similarity directly on the pitch-class multisets, without `addSpectra` partials applied to either side — that is, **pitch class similarity (PCS)**, not the spectrally enriched form (SPCS). The mislabelling dated back to v2.0.0 when the demos were first added; the implementations were always PCS. (`demo_triadSpcsGrid.{m,py}` remains correctly labelled — it does apply `addSpectra` and so genuinely is SPCS.) USER_GUIDE.md demo-table entries (§13) updated accordingly.


#### Time estimates and `verbose` options

- **`estimateCompTime` / `estimate_comp_time` — new `minPrintSec` parameter, defaulting to `10` s; `Ctrl+C` and print thresholds collapsed.** The function gains a fifth optional argument (`minPrintSec` in MATLAB / `min_print_sec` in Python). Estimates below the threshold are silent even when `verbose` is true; the default of 10 s is chosen so that sub-10 s waits are their own diagnostic and only genuinely-actionable workloads earn screen real estate. The previous separate "`Ctrl+C to cancel` suffix above 2 s" threshold has been collapsed into the same parameter — every printed estimate now carries the cancellation reminder by construction. The change is uniform across all callers (`evalMaet`, `simMaet`, `spectralEntropy`, `templateHarmonicity`, `virtualPitches`, and any user code that calls these in tight loops); no caller needs to opt in. Pass `0` to recover the old always-print behaviour, or set higher to surface only the slowest cases. Existing `verbose=false` callers retain full silence (unchanged).

- **New utility: `printBatchedEstimate` (MATLAB) / `maybe_print_batched_estimate` (Python).** Centralises the batched-mode upfront empirical-calibration print used by `templateHarmonicity`, `virtualPitches`, `spectralEntropy`, `entropyMaet`, and `tensorHarmonicity` batched dispatch helpers. Threshold and formatting are kept consistent with `estimateCompTime`'s scalar print path: 10-s default `minPrintSec` (or `min_print_sec`), every printed estimate carries `(Ctrl+C to cancel)`, and time-formatting uses the same units.

- **`templateHarmonicity` / `template_harmonicity` — `verbose` option and time estimates.** Both languages gain a `verbose` name-value argument (MATLAB) / keyword argument (Python), default `true`, controlling whether the function prints an upfront time estimate — matching the behaviour `evalMaet` and `simMaet` already had. Two estimation strategies, one per dispatch shape: scalar mode uses the kernel-only `estimateCompTime` / `estimate_comp_time` micro-benchmark; batched mode uses an empirical calibration that times a small sample of rows and extrapolates. The estimate is suppressed by `verbose=false`. Numerical results are unchanged.

- **`tensorHarmonicity` / `tensor_harmonicity` and `virtualPitches` / `virtual_pitches` — `verbose` option and time estimates.** Both functions gain a `verbose` name-value argument (MATLAB) / keyword argument (Python), default `true`, mirroring the `templateHarmonicity` addition. `tensorHarmonicity` scalar-mode forwards `verbose` to its inner `buildMaet` call (the dominant cost for tensor harmonicity is template construction, not template evaluation); `virtualPitches` scalar-mode prints a kernel-only `estimateCompTime` estimate covering its two `evalMaet` workloads. Both batched-mode helpers use empirical calibration. The estimate is suppressed by `verbose=false`. Numerical results are unchanged.

- **`spectralEntropy` / `spectral_entropy` — `verbose` option.** A `verbose` argument (default `true`) controls printing: scalar mode prints a kernel-only `estimateCompTime` estimate (sum of the dominant `evalMaet` workload, dim=1); batched mode prints an empirical-calibration estimate with warm-up, in the same idiom as `templateHarmonicity` batched.

- **`entropyMaet` / `entropy_maet` — `verbose` option for single-multiset batched dispatch.** A `verbose` name-value argument (MATLAB) / keyword argument (Python), default `true`, is added to the raw single-multiset batched dispatch. When enabled and `M > 1`, the function prints an empirical-calibration upfront estimate. `verbose=false` silences.

#### Other changes


- **Internal performance improvement for `r = 1` expectation tensors.** `buildMaet` (MATLAB) and `build_maet` (Python) now collapse equal-valued slots at build time when `r = 1`, in both the single-multiset and the multi-attribute (MAET) forms. In the MAET case the collapse is applied per-attribute independently — only attributes with `r_a = 1` are collapsed; attributes with `r_a >= 2` in the same event are unaffected. Mathematically exact: the density at `r = 1` depends on the source multiset only through its measure on the attribute's values, so events with the same value contribute additively to the same Gaussian kernel and can be merged into a single source point with the sum of the original weights. No behavioural change, no API change. Speedup is proportional to the degree of repetition in the input; for probe-tone-style contexts (e.g., where 7 unique context pitch classes are repeated 3 times) the effective speedup on downstream `evalMaet` and `simMaet` calls is approximately 9×. Not applied for `r >= 2`: at larger tuple sizes the source multiplicity carries information about within-tuple structure (e.g., the `r = 2` relative density at interval 0 receives genuine contributions from pairs of equal-pitched events) and collapsing would alter the density.

#### Performance

These entries cover inner-loop refinements to the kernel-evaluation paths in addition to the analytical-method gains documented above under *Möbius method*.

- **`simMaet` periodic-relative IP kernel: redundant component-wise outer wrap eliminated.** In the periodic-relative case the IP kernel previously applied an outer per-component wrap of the difference tensor before computing the pairwise-wrap quadratic form $Q$. Pairwise wrapping subsumes outer wrapping when both `rel` and `per` are true, so the outer wrap is redundant work. Removing it gives roughly 1.5–2× speedup on the cos-sim rel+per path in both languages. Applies symmetrically to the MAET log-kernel accumulator (`_ma_log_kernel` in Python; the corresponding helpers in `simMaet.m`), and the chunked and full single-multiset IP cores in `cosine.py`.

- **`templateHarmonicity` / `template_harmonicity` cross-correlation: `np.convolve` → `scipy.signal.correlate` (Python).** The chord-template cross-correlation at the heart of `templateHarmonicity` switches from `np.convolve(chord, tmpl[::-1])` to `scipy.signal.correlate(chord, tmpl, method='auto')`. Same numerical output; ~6× faster for the relevant template/chord sizes via SciPy's FFT-based correlation path at `method='auto'`'s crossover.

- **`evalMaet` / `eval_maet` periodic-relative kernel inner loop.** The pairwise-wrap loop introduced by the Eq 6 correctness fix (see *Fixed* below) uses vectorised slot-0 wraps and an in-place inner pair loop with preallocated workspaces in Python (`np.subtract / np.divide / np.floor / np.multiply / np.add` with `out=` parameters). The mixed vectorised/looped pattern bounds the worst-case end-to-end slowdown vs the prior (incorrect) algebraic form at ~2× rather than the ~4× a naïve pairwise-wrap implementation would impose. MATLAB sites use the same pattern (slot-0 wraps vectorised, inner pairs looped). Applies to every centres-path eval site in both languages.

- **`demo_triadConsonance` (MATLAB) and `demo_triad_consonance.py` (Python) — batched feature computation.** The inner double-loop that previously evaluated tensor harmonicity, template harmonicity, spectral entropy, and roughness one triad at a time over the upper triangle of the (interval1, interval2) grid (≈ 7,381 unique triads at the default `step = 10` cents in MATLAB / `step = 20` cents in Python) is restructured to use batched dispatch: tensor harmonicity in a single `evalMaet` / `eval_maet` call against a stacked query matrix; template harmonicity and spectral entropy each in a single call against an `(n_upper, 3)` chord matrix. Roughness, which does not accept batched input, remains in an explicit loop with progress reporting. Both batched sections print upfront time estimates ("estimated time ~X s [Ctrl+C to cancel]") in place of the previous per-iteration progress.

- **`demo_genChainSpcs` (MATLAB and Python) — full-range traversal.** Previously evaluated only the first half of the generator range `[0, period/2]` and reflected the result, as a perf workaround. The demo now evaluates the full range `[0, period)` directly and lets `simMaet`'s consumer-level dedup handle the redundancy internally — same result, simpler code, and the manual padding/trimming logic for non-evenly-dividing `genStep` values is gone.

#### Internal


- **Cross-language equivalence tests.** Hardcoded golden values pin down numerical agreement between the MATLAB and Python implementations to $10^{-8}$ relative across the new surface (Möbius-method cosine similarity on single-multiset and multi-attribute densities, Rényi-2 entropy on both, Möbius-method `tensorHarmonicity`, and Möbius-method `evalMaet`). See `tests/test_cross_language_golden.{m,py}`.

- **Cross-language speed parity for the Möbius method.** Targeted spot-checks at $(r, K) \in \{(2, 8), (3, 8), (3, 12), (4, 8), (5, 6)\}$ time the MATLAB Möbius-method IP/eval evaluators against their Python NumPy-einsum equivalents at matched inputs. The contraction graph is precomputed once per orbit at table-build time (see "Orbit-table contraction-graph precomputation" below) and consumed at runtime by `mobius.executeRecipe` (MATLAB) or `np.einsum(..., optimize=path)` (Python), avoiding per-call dispatch overhead in the contraction step. MATLAB / Python ratios are median 0.53× across the spot-check range (range 0.32×–1.37×, MATLAB generally the faster of the two at the median). The Möbius and Bulger methods remain mathematically equivalent at default settings; users do not need to choose between them. See `tests/bench_orbit_xlang.{m,py}` for the bench harness; `+mobius/buildContractRecipe.m` and `+mobius/executeRecipe.m` (MATLAB) and `_mobius._compute_einsum_path_*` (Python) for the implementations.

- **Orbit-table contraction-graph precomputation.** Each orbit table entry carries precomputed contraction-graph information embedded at build time:
  - **MATLAB** orbit structs carry three recipe fields (`recipeIP`, `recipeGrid`, `recipeBatched`) corresponding to the three IP-consumer call patterns (`mobius.innerProductOrbit`, `mobius.innerProductOrbitGrid`, `mobius.innerProductOrbitPwBatched`). Each recipe is a struct array of merge steps with precomputed `lhsPerm` / `rhsPerm` / dim-class counts. Runtime calls `mobius.executeRecipe`, which executes the recipe directly without invoking `intersect`, `setdiff`, `unique`, or `ismember`.
  - **Python** orbit entries carry three precomputed `np.einsum_path` outputs (`einsum_path`, `einsum_path_grid`, `einsum_path_pw_batched`) and one pre-built einsum string (`einsum_str_pw_batched`). Runtime calls `np.einsum(..., optimize=path)`, skipping NumPy's per-call path optimisation.

  Table loaders (`mobius.getOrbitTable` in MATLAB, `_mobius._ensure_paths` in Python) augment in-memory entries with these fields if absent from the loaded file, ensuring forward-compatibility with patch-version table additions.

- **Vectorised multi-dimensional truncated kernel-sum path.** `localTruncatedKernelSum` in `matlab/+internal/gaussianKernelSum.m` processes (query, neighbour-bucket) pairs in vector form: for each chunk of queries it expands all $3^{\text{dim}}$ neighbour buckets in one matrix operation, masks out-of-bounds neighbours and empty buckets via vectorised comparisons, expands each (query, run-bucket) pair into per-centre pairs via cumsum-based ragged indexing, and accumulates kernel sums via `accumarray`. Memory budgeting matches the exact path's heuristic (per-chunk peak $\sim (\text{dim} + 1) \cdot n_J \cdot \text{chunkSize}$ scalars, capped at 50% of `MaxPossibleArrayBytes` or a 4 GB fallback). Applies whenever `truncationSigmas` is finite and the workload is multi-dimensional; the 1-D path is separately vectorised along sorted centres.

- **Spatial cull on the relative periodic path (both languages).** Absolute periodic evaluation collapses the per-tuple kernel through its distinct-value table and the non-periodic paths cull on a bucket lattice; relative periodic evaluation culls too, rather than evaluating every tuple against every query. It admits a cull because the quadratic form bounds each wrapped coordinate. $Q = \left[\sum_k \mathrm{wrap}(D_k)^2 + \sum_{i<j} \mathrm{wrap}(D_i - D_j)^2\right] / r$ and the inner terms are non-negative, so a pair inside the truncation threshold has every $|\mathrm{wrap}(D_k)| \le \sqrt{r}\,k\sigma$; on that region no inner pair can wrap, so $Q$ there is exactly $w^{\top}(I - J/r)\,w$, whose inverse is $I + J$ — diagonal 2 — tightening the box to $\sqrt{2}\,k\sigma$ **independently of $r$**, a candidate set some eight times smaller at $r = 4$ than the a-priori bound gives. The lattice is pitched on the circle rather than on the centres' bounding box, with neighbour indices taken modulo the bucket count, so it wraps as the density does and needs no margin; the form is then evaluated exactly by the same expression the dense path uses and thresholded identically, so the result is the dense path's up to summation order. The gate stands the cull down where the truncation window is not narrower than the circle (fewer than three buckets around it) or where there are fewer tuples than the $3^{\text{dim}}$ neighbourhood lookup costs, falling back to the dense path. Measured on the diatonic scale at $\sigma = 15$, $r = 4$ unordered (840 tuples, 234k queries): 6.8× against a well-chunked dense path, and an order of magnitude against the `'auto'` chunk budget's very large chunks; neutral where the gate declines. Tests: `tests/test_periodic_cull.{py,m}`.


- **Culling on the joint-centres path of point evaluation (both languages).** A multi-attribute density with an attribute at $r_a = 1$ (an event list of onsets and pitches, say) or with a kernel covariance is evaluated over its joint tuple set, one centre per choice of a tuple from each attribute of an event. Each query meets only the centres within the truncation width on one culling coordinate — $k\sigma$ on an absolute attribute, $\sqrt{2}\,k\sigma$ on a relative one, whose coordinates are differences from position 0 — chosen as the coordinate whose centres spread furthest against that window; a full-image periodic attribute, whose wrapped Gaussian is evaluated untruncated, is never culled on. The path runs dense where culling would not pay, in chunks held to a cache-sized 8 MB working set beneath the `kernel_chunk_bytes` budget. In Python both the culled pairs, in groups of queries, and the dense chunks run on the kernel thread pool; on calls large enough to divide, four threads run the culled evaluation 2–3.6 times and the dense one 2–2.8 times as fast as one (measured on the maintainer's Mac). A culled pair is one the truncation would have zeroed, so values agree with the dense evaluation to summation order. Measured in Python on the maintainer's Mac: 141 to 32 µs per query at 10,000 centres over two attributes at $\sigma = 0.1$ (span 10), and 241 to 24 µs over 3000 events of an onset beside three pitches; the chunk cap alone gives 1.2–1.3× where the kernel is too wide to cull. The eval cost model prices the factored centres route and the factored Möbius evaluator, which take a density event by event, at $N$ times one event's cost, and the joint-centres path at its culled share; onsets beside a chord's pitches take the joint-centres path, 26–64 times as fast as the factored Möbius evaluator at 30 to 3000 events. Tests: `tests/test_ma_eval_cull.{py,m}`, and the cost-model blocks of `tests/test_time_estimate.py` and `tests/test_ma_eval_cost_model.{py,m}`.

- **Padded bucket lattice in the truncated kernel sums (both languages).** The spatial cull visits, for each query, the centres in its bucket's $3^{\text{dim}}$ neighbourhood. The lattice carries one empty bucket of margin on every face, so no neighbour of an occupied-region bucket can leave it, and the whole neighbourhood is the outer sum of one linear index per query and one linear displacement per offset — a single broadcast addition on precomputed lattice strides, with no bounds test or mask-copy. A neighbour outside the occupied region lands in a padded bucket, holds no centres, and is dropped by the occupancy test. Applies to `_truncated_kernel_sum_culled`, `_kernel._truncated_kernel_sum`, and MATLAB's `localTruncatedKernelSum`. Measured against a bounds-tested neighbourhood, the routine is 2.6–6.6× faster (Python, on grids of $10^5$–$10^6$ query points), least where the lattice is small relative to the query set, with bit-identical results. `tests/test_bucket_padding.{py,m}` pin the cull against a direct sum over the truncation ball, for queries outside the centres' bounding box — the case the margin exists for — as well as within it.

- **`kernel_threads` toolbox default, and threaded kernel arithmetic (Python only).** The elementwise Gaussian work that dominates every evaluation route is independent from one evaluation point to the next, and NumPy releases the interpreter lock inside its array loops, so the Python kernel paths spread it over a shared thread pool: `wrapped_gaussian_1d`, the exact and bucketed kernel sums in `_kernel.py`, the culled centres path in `_tensor/eval.py`, and the joint-centres path of multi-attribute point evaluation, culled and dense, in the same file. The split is into contiguous spans of evaluation points, and every point keeps the arithmetic it has serially — the image or harmonic sum runs within a point, and a query accumulates over its own centres in an order set by a bucket lattice pitched on the centres alone — so the values agree with the serial path to rounding at any thread count, bit for bit on most routes; only the elapsed time changes. The per-chunk byte budget is divided among the threads, leaving peak memory where it was serially, and threads are used only above an internal work threshold, so small calls are untouched. The `kernel_threads` default accepts `'auto'` (the factory value: `OMP_NUM_THREADS` when the environment sets it, else the core count capped at eight) or a positive integer, 1 being serial; set it to 1 when parallelising at a higher level, since a `multiprocessing` or `joblib` worker fanning out again oversubscribes the machine. MATLAB gains nothing here and has no counterpart: its runtime threads elementwise arithmetic itself and reduces each `parfor` worker to one computational thread. This is the divergence's whole substance — measured on a sixteen-core machine, MATLAB's `exp` runs 5.2× faster than NumPy's serially (0.47 versus 2.44 ns per element), which was the entire difference between the two languages' run times on a three-dimensional tensor-modes benchmark (37 s against 62 s). Scaling on that machine is about 7× on the kernel portion at eight threads, flattening thereafter as memory bandwidth saturates. Verified by `tests/test_kernel_threads.py`; documented in USER_GUIDE §11.3 and ARCHITECTURE §7.

- **`kernelChunkBytes` / `kernel_chunk_bytes` toolbox default.** All kernel-matrix workloads (centres-path and IP-path evaluators in both languages, plus the Möbius relative-mode evaluator) share a single per-chunk byte budget configurable via this default. The factory value `'auto'` resolves at call time to half of currently available physical memory (Linux `/proc/meminfo` `MemAvailable`; macOS `vm_stat` `free + inactive + speculative`; Windows `memory().PhysicalMemory.Available` in MATLAB and `GlobalMemoryStatusEx` via `ctypes` in Python). A 4 GiB fallback applies if all platform queries fail. Explicit positive-integer byte values override globally via `mptDefaults('kernelChunkBytes', N)` (MATLAB) or `mpt.set_default(kernel_chunk_bytes=N)` (Python). Per-query allocation estimates account for the broadcast difference tensor, its square, and the summed-then-exponentiated intermediate being briefly co-resident (`(2 \cdot \text{dim} + 2) \cdot n_J \cdot \text{bytesPerScalar}` for the broadcast-pattern sites; site-specific formulas for the IP-side and Möbius-relative paths). Resolution happens on every chunker call, so the budget tracks memory pressure across a session. The platform queries are factored into `internal.availableMemory` (MATLAB) and `mpt._utils.available_memory_bytes` (Python); resolution into `internal.kernelChunkBytesResolved` and `mpt._utils.kernel_chunk_bytes_resolved`.


- **Packaging.** The Python package now ships the pre-built orbit pickles via `[tool.setuptools.package-data]` in `pyproject.toml` (`mpt = ["_orbit_tables/*.pkl"]`); without this, the sdist/wheel build silently omits non-`.py` files and a fresh `pip install` would fall through to a multi-minute on-demand build on first `get_orbit_table()` call. `mpt.__version__` and the `pyproject.toml` `version` field are both `"3.0.0"`.

#### Design notes

**Additivity.** The v2.0 single-attribute calling conventions are preserved verbatim: `buildMaet(p, w, sigma, r, rel, per, period)`, `simMaet(p1, w1, p2, w2, sigma, r, rel, per, period)`, and friends keep their v2.0 calling conventions under the new names. The multi-attribute calling form is distinguished by passing `p` as a cell array (MATLAB) or list (Python) of per-attribute value matrices, so the single- and multi-attribute paths do not collide.

**MaetDensity slot layout.** For a relative attribute, `buildMaet` stores the effective-space Gaussian centres using a slot-0-anchored reduction: $v_i = u_{i+1} - u_0$ for $i = 1, \ldots, r-1$. This convention is inherited by all downstream consumers, including the cross-correlation shift lift in `sweptSimilarity`.

**Option II shape preservation.** All polymorphic dispatch paths preserve list shape: a length-1 list returns a length-1 cell / array, never a scalar. This matches NumPy and MATLAB cell-array semantics and makes downstream consumer code (e.g., a loop over the result) robust to single-element batches.

### Removed

#### `batchCosSimExpTens`, `cos_sim_exp_tens_raw`, and `eval_exp_tens_raw` are removed (breaking)

`batchCosSimExpTens` / `batch_cos_sim_exp_tens`, `cos_sim_exp_tens_raw`, and `eval_exp_tens_raw` are removed. #### The core entry points are renamed on the MAET (breaking)

| v2.0 | v3 |
|:---|:---|
| `buildExpTens` / `build_exp_tens` | `buildMaet` / `build_maet` |
| `evalExpTens` / `eval_exp_tens` | `evalMaet` / `eval_maet` |
| `cosSimExpTens` / `cos_sim_exp_tens` | `simMaet` / `sim_maet` |
| `entropyExpTens` / `entropy_exp_tens` | `entropyMaet` / `entropy_maet` |
| `ExpTensDensity` (Python) | `MaetDensity` |

The object these functions build, evaluate, and compare is the multi-attribute expectation tensor of Milne (2026), and the density carries the tag `MaetDensity`; the names say so, and the chain `packPreMaet` to `buildMaet` mirrors the pre-MAET to MAET of the manuscript's Definition 2.6. `cosSimExpTens` also became `simMaet` rather than a name in `cosSim`, since cosine is one of three settings of `normalize` and the other two are not cosine similarities.

The old names are removed outright rather than deprecated: v3 is a major release, and a shim for the toolbox's most-used entry points would carry the superseded vocabulary through every example and docstring. Error and warning identifiers move with the functions, so `cosSimExpTens:badMethod` is now `simMaet:badMethod` and a `try` / `catch` matching the old identifiers needs updating.


#### `normalize` kwarg removed across all entropy entry points (breaking)

The v2.0 `normalize` boolean kwarg has been **removed** from `entropyMaet` / `entropy_maet`, `spectralEntropy` / `spectral_entropy`, and `nTupleEntropy` / `n_tuple_entropy`. The four-method API supersedes it: `method='shannon'` returns raw discrete $H = -\sum q \log_b q$, and `method='normalized'` returns the Pielou-style ratio $H/\log_b(N) \in [0, 1]$ (the v2.0 default behaviour). The continuous methods `'differential'` and `'renyi2'` are continuous-form entropies and have no $[0, 1]$ reference. Passing `normalize` to any of the three entry points now raises a migration error identifying the calling function and pointing to the replacement methods.

- **`entropyMaet` / `entropy_maet`**: signature no longer accepts `normalize`. Default `method='shannon'` returns raw $H$ (was previously equivalent to `method='shannon'` with `normalize=true`, i.e. $H/\log_b(N)$); call with `method='normalized'` to recover the v2.0 default value. The MATLAB function scans `varargin` directly before the NV-pair parser to surface the migration error early; the Python entry point uses a `**legacy_kwargs` catch.

- **`spectralEntropy` / `spectral_entropy`**: signature no longer accepts `normalize`. Default is already `method='differential'` (the principled scale-free quantity for cross-density comparison); the MATLAB function uses an `arguments`-block sentinel default `nvArgs.normalize = []` to detect the legacy kwarg, the Python entry point uses `**legacy_kwargs`. The delegate no longer threads `normalize` through to `entropyMaet`.

- **`nTupleEntropy` / `n_tuple_entropy`**: as already documented above; defaults to `'normalized'` so v2.0 callers with the default get the same value without code changes.


- **Migration message format.** The error message names both replacement methods and explains why `'differential'` and `'renyi2'` have no `[0, 1]` reference, so v2.0 callers can pick the correct method without re-reading the docs.


#### `convertPitch` / `convert_pitch`

- Removed; replaced by the bare-array form of `transformAttributes` / `transform_attributes` (see Added). Every call site in the toolbox, the demos, and the guide is migrated; the mapping is mechanical, `convertPitch(x, 'a', 'b')` → `transformAttributes(x, [], {'a', 'b'})` and `convert_pitch(x, 'a', 'b')` → `transform_attributes(x, None, ('a', 'b'))`.

### Fixed

#### `evalMaet` periodic-relative quadratic form

- **`evalMaet` / `eval_maet`** — Fixed the periodic-relative quadratic form $Q$ to use the pairwise-wrap form (Eq 6 of the preprint), matching `simMaet` and the JMM Eq. 3.4 integral form to $O((\sigma/P)^{\infty})$. Previously the centres-array path used the algebraic-with-outer-wrap form $Q = \sum_k \mathrm{wrap}(D_k)^2 - (\sum_k \mathrm{wrap}(D_k))^2 / r$ inherited from the v1 implementation — a per-component-image approximation that diverges from the pairwise-wrap form when within-tuple pairwise differences cross $\pm P/2$. The same correctness fix was applied to `simMaet` in v2.0.1; the parallel fix in `evalMaet` was overlooked at the time and is now applied. At typical perceptual $\sigma/P \le 0.03$ the two forms agree as $O((\sigma/P)^{\infty})$; above the threshold the difference becomes measurable. Affects the single-multiset centres eval sites and the multi-attribute per-attribute eval sites in both languages; non-periodic and absolute results are unchanged.

#### `eval_maet`: a list of query points

- **`eval_maet`** (Python) – A plain list of numbers given as the query points of a one-dimensional density, `eval_maet(dens, [5, 6, 7])`, was read as one entry per attribute and raised an `IndexError`; it is now read as the 1-D array of query points that the user guide (§10.9) describes, as a NumPy array already was. MATLAB is unaffected.

#### Entropy

- **`entropyMaet` (MATLAB) / `entropy_maet` (Python) — single-attribute density entropy at `dim > 1`.** v2.0's single-multiset path constructed a 1-D query grid, which errored when `dim > 1` (for example, `r = 2, rel = false`). The grid is now the Cartesian product over the density's dimensions. A `gridLimit` guard (default `1e8`) prevents accidental allocation of ruinously large grids; users can raise the ceiling explicitly when working at high `nPointsPerDim` and `dim`.

- **`entropyMaet` (MATLAB) / `entropy_maet` (Python) — empty weights mean uniform.** Passing `[]` (MATLAB) or `None` (Python) for `w` is now explicitly documented as equivalent to uniform weights `ones(numel(p), 1)`. The behaviour was already correct in MATLAB by virtue of `buildMaet`'s handling of empty weights, but Python's previous implementation rejected `w=None` in the single-multiset path; both now accept it consistently.

## [2.0.0] — 2026-04-05

### Overview

Version 2.0.0 is a major rewrite of the Music Perception Toolbox. Analytical methods have replaced the previous numerical approximations wherever feasible (entropy computation, which has no known closed-form solution for Gaussian mixtures, remains discretized). The expectation tensor core has been restructured around precomputed density objects (`buildExpTens`), with fully vectorized computation and automatic memory-aware chunking. All existing functions have been given clearer names and a consistent interface, and a Python implementation has been added. The v1 dependency on the [Sparse Array Toolbox](https://github.com/andymilne/Sparse-Array-Toolbox) has been eliminated; v2 has no external dependencies.

Accessibility has been substantially improved: every function now includes a full help text with usage examples, a User Guide covers the conceptual foundations and provides a complete function reference for both languages, and nine demo scripts (in both MATLAB and Python) cover all major use cases.

The original `cosSimExpTens` function by David Bulger is preserved with full backward compatibility: the v1 nine-argument calling convention still works unchanged.

### Added

The following functions are entirely new in v2 (no v1 equivalent):

- **`buildExpTens`** — Precomputes an r-ad expectation tensor density object as a struct that can be reused across multiple calls to `evalExpTens` and `cosSimExpTens`.
- **`evalExpTens`** — Evaluates the expectation tensor density analytically at arbitrary query points with automatic memory-aware chunking and three normalisation modes. (Together, `buildExpTens` and `evalExpTens` replace `expectationTensor`, which built a discretized tensor on a grid.)
- **`batchCosSimExpTens`** — Batch cosine similarity of paired pitch multisets with automatic deduplication of repeated pairs, optional spectral enrichment, and progress reporting.
- **`estimateCompTime`** — Micro-benchmark-based computation time estimator, calibrated to the user's hardware.
- **`templateHarmonicity`** — Harmonicity via template cross-correlation (returns both hMax from Milne 2013 and hEntropy from Harrison & Pearce 2020).
- **`tensorHarmonicity`** — Harmonicity via expectation tensor lookup: evaluates the relative r-ad density of a harmonic series at the chord's intervals.
- **`virtualPitches`** — Virtual pitch (fundamental) salience profile via template cross-correlation.
- **`convertPitch`** — Converts between seven pitch/frequency scales (Hz, MIDI, cents, mel, Bark, ERB-rate, Greenwood cochlear position).
- **Python implementation** — A functionally identical Python package (`mpt`) using NumPy and SciPy. Python uses snake_case naming (e.g., `cos_sim_exp_tens`, `add_spectra`); a few names are shortened where the MATLAB suffix is redundant in a package namespace (e.g., `balanceCircular` → `balance`, `evennessCircular` → `evenness`). See the [User Guide](USER_GUIDE.md#4-api-conventions-matlab-vs-python) for the full mapping and calling convention differences.

### Changed

- **`cosSimExpTens`** — Now additionally accepts precomputed density structs from `buildExpTens` (preferred for repeated comparisons). The original nine-argument calling convention is fully backward compatible. David Bulger's analytical algorithm — which inspired much of the v2 architecture — has been further optimized at the implementation level: the double loop over all pairs of r-ad index sets has been replaced by fully vectorized array operations (3D implicit expansion and matrix multiplication), the explicit Riemannian metric matrix has been eliminated in favour of direct scalar arithmetic, and automatic memory-aware chunking has been added for large problems. Tuple enumeration and weight computation are factored into the precomputed density struct returned by `buildExpTens`, so these are computed once and reused across the three inner product calls (⟨x,x⟩, ⟨y,y⟩, ⟨x,y⟩) and across multiple comparisons. Added `'verbose'` flag for suppressing console output.

### Breaking changes

- Function names, signatures, and argument ordering have changed throughout. Code that called only `cosSimExpTens` with its original nine-argument signature will continue to work without modification. Code that relied on other v1 functions will need to be updated — see [MIGRATION.md](MIGRATION.md) for a complete mapping.
- The v1 dependency on the [Sparse Array Toolbox](https://github.com/andymilne/Sparse-Array-Toolbox) has been eliminated. v2 has no external dependencies.

### Removed

- `cosSim` / `expTensorSim` → absorbed into `cosSimExpTens` (which computes the similarity analytically)
- `gaussianKernel`, `histEntropy`, `tensorSum`, `circConv` → absorbed as internal computations
- `pitch2Ind` / `ind2Pitch` → no longer needed (v2 evaluates densities at continuous query points)
- `contextProbeSpecSim` → superseded by the combination of `addSpectra` + `cosSimExpTens`
- `noiseSignal` → noise-floor estimation incorporated into `audioPeaks` via `'noiseFactor'`
- `nonLinDps`, `pDist` → not carried forward
